### ⚠️ UTF-8 BOM 필수

일본어 로캘 VS 는 BOM 없는 파일을 **CP932(Shift-JIS)** 로 읽는다. 한국어 주석이 깨질 뿐 아니라
**개행까지 먹혀 코드가 사라진다** (실제로 `CreateWindowExW` 인자 2개가 사라져
「関数に 10 個の引数を指定できません」에러가 났다).

`Write` 툴은 BOM 없이 쓰므로 **파일을 만들거나 고친 뒤 반드시** 이걸 실행한다:

```powershell
Get-ChildItem -LiteralPath "D:\イジュンハ\3.DX\DX11_Bubble\DarkBubble\src" -Recurse -File -Include *.cpp,*.h | ForEach-Object {
    $t = [System.IO.File]::ReadAllText($_.FullName, (New-Object System.Text.UTF8Encoding $false))
    [System.IO.File]::WriteAllText($_.FullName, $t, (New-Object System.Text.UTF8Encoding $true))
}
```

컴파일러 쪽은 프로젝트 옵션의 `/utf-8` 이 담당한다(이미 설정됨).

### 빌드 명령

```powershell
$msbuild = & "${env:ProgramFiles(x86)}\Microsoft Visual Studio\Installer\vswhere.exe" -latest -requires Microsoft.Component.MSBuild -find "MSBuild\**\Bin\MSBuild.exe" | Select-Object -First 1
& $msbuild "D:\イジュンハ\3.DX\DX11_Bubble\DarkBubble\DarkBubble.vcxproj" /p:Configuration=Debug /p:Platform=x64 /v:minimal /nologo
```

빌드가 끝나면 사용자에게 **「VS 다시 로드 → F5」** 라고 알린다.

둘 다 **멱등**하다 — 몇 번 돌려도, 어느 순서로 돌려도 결과가 같다.

`.ps1` 도 **UTF-8 BOM 이 필요하다** — 한국어 주석이 CP932 로 오독되면 파싱까지 깨진다.
C++ 파일과 같은 함정이다.

| **F2** | 갑옷 갈아입기 (CLOTH poise 10 ↔ PLATE poise 24). **임시** — 6단계에서 버린다 |
| **F4** | **다리 파괴 ↔ 복구.** 엎드린 자세를 바로 만들어 판정 상자·중단 회피를 확인한다. **임시** |
| **F1** (추가) | 적의 **시야 부채꼴**도 같이 보인다. 파랑 = 아직 안 보임 / 빨강 = 들켰음. 노란 사각형 = 청각 반경 |
| **F3** | FPS / TPS / 틱 / Scene / 텍스처 캐시 오버레이 |
| **`,`** | 프레임 정지 |
| **`.`** | 1틱 전진 |
| **`/`** | 슬로우 모션 (1/8) |

> 실제로 accumulator 를 두 번 더해 2배속이던 버그가 있었다.

★ 6-c ~ 6-f 는 **전부 2026-09-10 에 추가된 방향 전환**이다. design.md §3.8 / §3.9 / §4 참조.
JSON(6-g)을 맨 뒤로 미룬 이유는 중력·발판·카메라·시야가 전부 **새 데이터**를 만들기 때문이다 —
그릇을 먼저 만들면 스키마에 계속 얹어야 한다. 무브셋을 JSON 보다 먼저 한 것과 같은 논리다.

**★ 6-c 의 핵심 — 시점 전환**: 이 게임은 **측면 뷰 플랫포머**다(design.md §3.8).
`README.md` 와 이 문서는 처음부터 「버블보블 같은」이라고 적어 두었는데
`design.md` §4 는 젤다 / Isaac(탑다운)을 참조로 들고 있었고, 코드는 그 사이에서
**벨트스크롤**(`y` = 깊이, 상하좌우 자유 이동)로 흘러갔다. 셋이 서로 다른 게임이었다.
2026-09-10 에 버블보블 쪽으로 확정했다.

> `y` 의 의미가 **깊이 → 높이**로 바뀐다. 중력이 붙고 이동이 좌우만 남는다.

★ 지금까지 만든 것은 거의 전부 살아남는다 — 상태 머신 · 프레임 데이터 · 스태미나 ·
강인도 · 부위 파괴 · 무브셋 · 사망/부활. 오히려 **부위 파괴는 측면 뷰에서 더 잘 읽힌다**
(머리·몸통·다리가 화면에서 위아래로 늘어선다).
바뀌는 것은 이동과 충돌, 그리고 적의 추격이다.

**6-e 의 핵심**: 지금까지 `constexpr` 로 박아 둔 것들(AttackData / RollData / HurtData /
ArmorData / PartBox / AnimationClip)이 전부 JSON 으로 빠진다.
★ **무브셋을 먼저 만든 덕분에 스키마가 확정되었다** — 무기 하나가 공격 여러 개를
가진다는 계층이 실제로 필요하다는 것이 코드로 증명되었다.

★ JSON 의 진짜 이득은 파일을 밖으로 빼는 것이 아니라 **핫 리로드**다.
빌드 없이 숫자를 바꿔 확인할 수 있으면 밸런싱 왕복이 40초에서 2초가 된다.
`Assets.cpp` 에 「핫 리로드가 필요해지면 그때 Reload() 를 추가하면 된다」고
적어 둔 그 자리다.

★ 플랫포머 전환을 **JSON 보다 먼저** 두는 이유: 중력·점프·발판이라는 새 데이터가
생기는데, 그릇을 먼저 만들면 스키마에 또 얹어야 한다. 무브셋을 JSON 보다 먼저 한 것과
같은 논리다 — **구조가 확정된 뒤에 그릇을 만든다.**

**파서 미결정**: `nlohmann/json`(헤더 하나) / 직접 작성 / 더 단순한 형식.
「외부 엔진을 안 쓴다」는 원칙이지 「라이브러리를 안 쓴다」는 아니다(DirectXTK 를 쓴다).

`docs/design.md` 에 상세히 있다. 요약:

|---|---|
| 내부 해상도 | **640x360 을 x2 확대.** 좌표·속도·히트박스는 전부 640x360 기준 |
| 전투 | **완전 스태미나제**(다크소울식) |
| 스태미나 고갈 | **방식 B** — 부족해도 행동이 나가고, 0 미만이면 경직 |
| 부위 파괴 | **핵심 시스템. 적과 플레이어 둘 다.** 부위 5개(머리/왼팔/오른팔/몸통/다리). 머리·몸통=즉사, 팔=무기 낙하 + **몸통의 완충재**, 다리=이동 불가(플레이어는 구르기 상실). **절단 있음** (design.md §3.2.2) |
| 다리 | 좌/우로 나누지 않고 **하나** |
| 부위 선택 | **겹침 면적이 가장 큰 부위**에 데미지. 단 중단 공격은 팔이 살아 있으면 팔이 먼저 받는다 |
| 강인도 | **적도 가진다.** 잡몹 15. 강한 공격(impact 16/18)으로 적의 공격을 끊을 수 있다 (design.md §3.1.1) |
| 무기 | **오른손이 기본, 잘리면 땅에 떨어진다.** 주우면 남은 손에 든다. **죽어도 그 자리에 남는다** (design.md §3.2.2.1) |
| 물기 | 무기 없이 쓰는 최후의 수단. **머리 높이 = 즉사 노림.** 우클릭, 언제든 |
| HP 표시 | **HP 바 없음.** 좌하단 몸 그림에서 부위가 붉어진다 (design.md §3.2.3) |
| 주인공 | **1명** (마을 유일 생존자인 아이). 스타팅 캐릭터 복수안은 폐기 |
| 지문 슬롯 | **2개** (기회비용을 만들기 위해) |
| 장비 | **강해지는 것이 아니라 「무엇을 포기하는가」.** 무거운 갑옷은 경직을 막지만 HP 로 지불한다 (design.md §3.10) |
| 엔진 경계 | **두 번째 사용자가 생겼을 때 엔진으로 올린다.** 미래 예측이 아니라 관찰로 정한다 (design.md §9) |
| 컴포넌트 시스템 | **아직 만들지 않는다.** 엔티티가 2개뿐이라 「두 개짜리 범용 프레임워크」가 된다 |
| 맵 | ~~고정화면 방 그래프~~ → **넓은 맵 + 카메라 추적** (2026-09-10 변경, design.md §4) |
| 시점 | **측면 뷰 플랫포머** — 중력 · 점프. `y` 는 깊이가 아니라 높이 (design.md §3.8) |
| 시야(FOV) | **적의 시야 + 플레이어의 어둠 둘 다 확정.** B(적) 먼저, A(어둠) 나중 (design.md §3.9) |
| 서사 전달 | **컷신 없음.** 환경·기도문·임종대사·환영으로 |
| 상태 머신 | **enum + switch.** 다양성은 **데이터**에서 나온다(공격 5종이어도 `Attack` 은 하나). 상태 자체는 「조건이 여러 곳에 흩어지면 승격」한다 — 그래서 점프는 상태다(8개) |
| 상태 길이 | **프레임 데이터가 정한다.** 애니메이션의 `Finished()` 로 판정하지 않는다 |

## 8. 이미 밟은 함정 (반복하지 말 것)

| 함정 | 내용 |
|---|---|
| BOM 없는 UTF-8 | CP932 로 오독 → 개행까지 먹혀 코드가 사라진다 |
| `/utf-8` 없이 좁은 문자열 | 실행 문자셋이 CP932 라 한국어가 컴파일 시점에 깨진다 |
| `DrawText` | `windows.h` 가 매크로로 정의 → `DrawTextW` 로 치환된다. `DrawString` 으로 명명 |
| `min`/`max` | `NOMINMAX` 필수 (이미 설정됨) |
| accumulator 이중 가산 | 리팩터링에서 옮길 줄을 지우지 않고 복사 → 2배속 |
| `m_playerAnim.Tick()` 누락 | 리팩터링에서 옮기지 않음 → 애니메이션 정지 + Attack 에서 못 빠져나옴 |
| 프레임 경계 D3D 해저드 | `SpriteBatch::End()` 가 SRV 를 풀지 않아 다음 프레임 RTV 바인딩과 충돌. `EndFrame` 끝에서 `PSSetShaderResources(nullptr)` |
| `ResizeBuffers` 전 참조 | RTV 와 **컨텍스트 바인딩** 둘 다 놓아야 한다 |
| 엣지 입력 소실 | 틱이 0회 도는 프레임에서 사라진다. `Input` 이 `ConsumeEdges` 까지 붙잡아 둔다 |
| `SceneManager::Replace` | 먼저 비우고 Enter 가 실패하면 게임이 조용히 종료. 새 Scene 을 먼저 올려 본다 |
| `AnimationPlayer::Play` 비교 | 모든 필드를 비교해야 한다. row/frameCount 만 보면 속도 변경이 무시된다 |
| AABB 좌우 반전 | `facing = -1` 이면 `left > right` 가 되어 `Intersects` 가 절대 참이 안 된다. min/max 정규화 필수 |
| 소수 좌표로 그리기 | 시트의 옆 칸을 물어와 1픽셀 선이 생긴다. **계산은 소수, 그리기는 정수** |
| 부위 파괴 중복 히트 | active 3틱이면 데미지 3번. 「이번 휘두르기에 이미 맞췄나」 표시 필수 |
| 자세별 판정 상자 | 엎드렸는데 상자가 서 있는 위치면 공중에 뜬다. 자세마다 상자를 따로 |
| 원형 거리로 사거리 판정 | 히트박스는 **가로로 뻗는다.** 위아래로 34px 떨어지면 거리는 사거리 안인데 상자가 안 닿아 적이 허공을 영원히 후려친다. 가로·세로를 따로 볼 것 |
| 「멈추는 거리」≠「공격 사거리」 | 두 숫자로 두면 「멈췄는데 못 때리는」 적이 생긴다. **같은 조건 하나**를 쓸 것 |
| 공격 종류를 매 틱 판정 | 휘두르는 도중에 다리가 부서지면 프레임 데이터가 통째로 바뀌어(60→54틱) active 를 건너뛴다. **시작 시점에 고정**(`attackIsBite`) |
| 피격 무적 == 경직 길이 | 경직이 풀리는 그 틱에 다시 맞는다 = 스턴락. **무적을 더 길게** |
| 고갈 경직 중 피격 | 경직이 풀려 **피격이 이득**이 된다. 처음엔 들어오기 전 상태를 기억하는 필드로 막았는데, 고갈 래치를 `StaminaComponent` 로 옮기자 **그 필드가 통째로 필요 없어졌다.** 상태를 올바른 주인에게 두면 방어 코드가 저절로 사라진다 |
| 팔 테두리가 몸통 안에 | 도트 그림에서 1픽셀 검은 선은 「팔」이 아니라 「몸에 난 금」으로 읽힌다. 팔 끝을 몸통 테두리에 정확히 붙일 것 |
| 애니메이션과 판정 틱 불일치 | `startup / ticksPerFrame` 이 정수가 아니면 타격 그림과 판정이 어긋나 **플레이어가 학습할 수 없다.** 데이터를 2~3틱 반올림하는 편이 싸다 |
| ★ 조건을 「상태 목록」으로 쓰기 | `state == Crawl` 로 자세를 골랐더니, 상태를 하나(`Attack`) 추가한 순간 엎드린 적의 판정 상자가 공중에 떴다. **「몸의 성질」로 쓸 것** — `EnemyLegsBroken()`. 그러면 상태를 더 늘려도 다시 안 고친다 |
| ★ 디버그 키를 틱 안에서 읽기 | 엣지 입력은 틱이 0회 도는 프레임에서 사라진다. F1 이 **프레임 정지 중 100% 무시**되고 60Hz 초과 모니터에서 절반이 씹혔다. **바꾸는 대상으로 자리를 정한다** — 표시만 바꾸면 Game 이 프레임당 1회, 게임 상태를 바꾸면 누적 엣지 |
| 같은 일을 두 곳에서 | `UpdateMovement` 가 발소리 쿨다운을 채우고 `ChangeState(Run)` 이 0으로 되돌려, 달릴 때마다 발소리가 1/60초 간격으로 두 번 났다. 「살짝 두꺼운 한 번」으로 들려서 눈치채기 어렵다 |
| 에셋에 디버그 표시 굽기 | 초기 생성 스크립트가 각 셀에 프레임 번호를 그려 넣었고, 그것이 **게임 화면에 색 점으로 렌더**됐다. 원점이 발밑이라 캐릭터 왼쪽 위에 떴다. 디버그 표시는 코드로 그릴 것 |
| 크기 상수 흩어놓기 | `Window.cpp` 가 캔버스 크기를 `640, 360` 으로 하드코딩. 내부 해상도를 바꾸면 최소 창 크기만 옛 값으로 남는다. `Constants.h` 를 include 할 것 |
| 부호 없는 인덱스 계산 | `m_stack.size() - 1` 은 빈 스택에서 `SIZE_MAX`. 호출자가 막아 주더라도 **함수 자신이 안전해야** 세 번째 호출자가 생겼을 때 안 죽는다 |
| ★ 「내가 다시 불렸다 = 위가 사라졌다」 추측 | 틀린다. 한 프레임에 틱이 여러 번 도는데 Scene 전환은 프레임 끝에 **한 번만** 적용되므로, 전환을 요청한 프레임의 다음 틱에서 오판한다. `Scene::Resume` 같은 **명시적 통지**가 필요하다 |
| 초기화와 리셋을 두 벌로 | 필드를 추가할 때 한쪽만 고쳐 「두 번째 판부터 이상하다」가 된다. `Enter` 가 `Respawn` 을 부르게 해서 한 곳으로 모을 것 |
| 리셋에서 `ChangeState` 호출 | 「같은 상태로의 전이는 무시」에 걸려 아무 일도 안 일어난다. 리셋은 상태를 직접 놓고 애니메이션을 `forceRestart` 로 다시 걸 것 |
| Scene 전환을 틱마다 요청 | 한 프레임에 틱이 여러 번 돌면 `Push`/`Pop` 이 여러 번 요청되어 「전환이 두 번 요청됨」 경고가 난다. 요청했음을 표시할 것 |
| ★ 같은 것을 두 곳에서 막기 | 콤보 무한 연타를 「예약할 때」와 「고를 때」 양쪽에서 막았더니, 고르는 쪽이 **이미 올라간 카운터**를 봐서 콤보가 아예 안 나왔다. 빌드도 통과하고 죽지도 않는 「그냥 안 되는」 버그다. **막을 곳은 한 곳** |
| ★ 같은 것을 **두 곳에서 그리기** | 부위 상자가 생긴 뒤에도 `PlayerController::Hurtbox()`(고정 44px)가 디버그 표시에 남아 있었다. 판정에는 안 쓰였지만 자세를 안 따라가서 **「엎드렸는데 상자는 서 있는」 거짓 표시**가 났다. 정보(무적 여부)는 다른 곳으로 옮기고 상자는 지웠다 — 「안 쓰이니 놔두자」가 가장 오래 가는 거짓말이 된다 |
| ★★ 쓰이지 않는 값이 **속도를 훔친다** | `MoveIntent {x, y}` 를 길이로 정규화하고 있었다. 플랫포머가 되면서 `y` 는 **아무것도 움직이지 않게** 되었는데 정규화에는 계속 참여해서, ↑를 같이 누르면 가로 속도가 **0.707배**가 되었다. 값을 고치지 않고 **개념을 지웠다** — 축이 하나뿐인 게임에 2차원 벡터를 두면 언젠가 두 번째 축이 몰래 끼어든다 |
| ★★ 이름이 좌표계를 속인다 | `PanFromCanvasX(worldX)` — 월드가 캔버스와 **같은 크기**인 동안에는 맞았다. 맵이 넓어지는 순간 옆에서 나는 소리가 화면 끝에서 들린다. 둘 다 `float` 라 컴파일러가 모른다. **좌표를 받는 함수는 어느 좌표계인지 이름에 적을 것** — 그리고 바꿀 때 **이름을 바꾸면** 호출부가 전부 에러가 된다(§9.1) |
| 카메라 위치의 반올림 | 흔들림 오프셋만 반올림하고 카메라 위치는 소수로 두면 **화면 전체**가 격자에서 밀려 도트가 뭉개진다. 「계산은 소수, 그리기는 정수」가 카메라에서는 **화면 단위**로 적용된다 — `m_x` 는 소수로 두고 `ViewMatrix` 에서만 반올림 |
| ★★ 「전용 그림이 없으니 예외로」 | 자세별 공격 그림이 없어서 `Prone() ? 기어가기 : 공격그림` 으로 때웠다. 그 행은 **반복**이라 엎드려 공격하면 **아무 일도 안 일어나 보였다.** 그림을 그리자 예외가 통째로 사라졌다 — **공격 데이터가 자기 그림을 들고 다니면 분기가 필요 없다** |
| 자세가 몸의 **모양**을 바꾸면 사거리도 | 엎드리면 머리가 **앞으로 나간다**(상자 x 4~20). 서 있을 때의 `reach 4` 를 그대로 쓰니 물기 판정이 **제 머리 위**에 얹혀 2픽셀밖에 안 튀어나왔다. 자세별 데이터는 **높이만 바꾸면 끝이 아니다** |
| 자세가 늘면 **조합**이 늘어난다 | 자세 3 x 공격 2(무기·물기) = 6 가지 그림이 필요하다. 하나를 채우면 나머지가 빈 것이 드러난다. 자세를 늘릴 때는 **조합표를 먼저 그려 볼 것** |
| ★ 「자세는 따라가면 안 된다」는 성급한 결론 | 지형 상자를 자세와 무관하게 고정해 두고 「따라가면 발판 속으로 내려앉는다」고 적었는데 **틀렸다.** 원점이 발밑이라 상자는 **위에서** 줄어든다 — 발은 그대로다. 그대로 뒀다면 발판 아래 32픽셀 틈을 **서서도 웅크려도 못 지나가는** 채로 남았을 것이다 |
| 가만히 커지는 상자 | 세로 충돌은 「움직이는 중」(`dy != 0`)에만 해결된다. 그래서 낮은 틈에서 일어서면 **아무도 밀어내지 않아 천장 속에 박힌다.** 상자가 커질 수 있으면 **커져도 되는지 먼저 묻는** 함수(`CanStandUp`)가 반드시 함께 있어야 한다 |
| 좌표를 직접 옮기는 곳이 여럿 | 지형 충돌이 들어오자 `tr.x` 를 직접 쓰던 세 곳(걷기·구르기·넉백)이 전부 벽을 통과했다. **이동은 문 하나(`BodyComponent::MoveX`)로 모을 것** — 하나라도 새면 그 이동만 규칙 밖이 된다 |
| 화면 경계를 clamp 로 | 이동마다 `std::clamp` 를 걸고 있었다. 화면 끝을 **지형(벽)으로** 두면 걷기·구르기·넉백이 전부 같은 규칙으로 막힌다 — **예외를 없애려면 그것도 규칙 안에 넣는다** |
| ★★ 발판 배치 — 「올라갈 수 있는가」는 점프 높이만의 문제가 아니다 | 세로 간격 40 / 두께 8 이면 **틈이 32** 인데 몸이 44 다. 그 사이에 설 수 없으니 강제 웅크리기가 걸리고, 웅크리면 점프가 막혀 **영영 못 올라간다.** 조건은 셋이다: ① 간격 < 점프 정점 ② **틈(간격-두께) > 몸 높이** ③ 가로 간격 < 공중 이동 거리. 스폰 자리도 비울 것 |
| 공식값과 적분값 | `v0²/2g` 는 연속시간 공식이다. 틱마다 더하는 이상 실제 정점은 그보다 낮다(7.0/0.35 → 공식 70, 실제 **66**). **세어 볼 것** |
| 시차 배경은 **화면 밖으로도 밀려난다** | 배경을 지면 근처에서 시작했더니 세로 시차가 아래로 밀어 **지면에 가려 하나도 안 보였다.** 시차가 움직이는 만큼 **크게 그려 두어야** 한다 |
| 배경 대비를 한쪽으로만 | 두 층 다 배경 지우기 색(0.10)보다 어둡게 칠했더니 서로 구분이 안 됐다. **양쪽으로 벌릴 것** — 먼 층은 옅게(공기에 묻힌다), 가까운 층은 짙게(실루엣) |
| ★ 속도에 「더하기」 | 넉백의 「살짝 뜨기」를 `velocityY -= lift` 로 했더니, **점프로 올라가는 중에 맞으면** 상승 속도에 얹혀 훨씬 높이 날아올랐다. 「띄운다」는 **「이만큼 뜨게 만든다」**이지 「이만큼 더 뜬다」가 아니다. 속도를 다루는 함수는 **가산인지 대입인지를 이름과 주석에 박아 둘 것** |
| ★★ 눌러서 만든 자세는 판정을 안 데려온다 | 웅크리기를 `SetScale` 로 표현했더니 그림만 낮아지고 판정 상자는 선 채였다. 비율을 키워 맞추려 했지만 머리까지 납작해져 다른 캐릭터가 됐다. **전용 그림을 그리는 것이 결국 싸다** — 그림과 판정이 같은 숫자(발끝 27)에서 만난다 |
| 「스프라이트에 콜라이더 자동」의 한계 | Unity 도 콜라이더를 **붙일 때 1회** 맞춰 줄 뿐 애니메이션을 따라가지 않는다. 게다가 여기선 실루엣에 **무기가 들어가고**(thrust 행 상단 62 = 칼끝) 부위 5개를 구분할 수 없다. **실루엣은 그림이고 부위는 기획이다** |
| ★★ 그림만 바꾸고 판정은 안 바꾸기 | Ctrl 웅크리기가 스프라이트만 눌렀고(`SetScale`) 판정 상자는 선 채였다. **화면은 「낮아졌다」고 말하는데 판정은 「서 있다」고 말한다.** 자세를 바꾸는 것은 그림이 아니라 **몸**이어야 한다 — 이제 그림과 판정이 `Crouched()` 하나를 같이 본다 |
| 「나중에 상태로 승격」이 항상 답은 아니다 | design.md 가 「웅크린 판정이 달라지면 상태로 올린다」고 적어 두었는데, 막상 그때가 오니 **올리면 안 됐다** — 웅크리기는 공격과 **공존**해야 하고 상태 머신은 한 번에 하나다. 승격 대상은 상태가 아니라 **자세**였다 |
| ★★ 도달할 수 없는 기능 | 플레이어의 다리 40 HP 를 **아무도 건드릴 수 없었다.** 잡몹은 중단만 휘두르는데 다리는 그 아래에 있었고, 물기는 「누군가 엎드렸을 때」만 나왔다 — **엎드려야 물고, 물려야 엎드리는** 순환. 부위·엎드리기·기어가기 전부가 코드에는 있는데 게임에는 없는 상태였다. **숫자를 넣었으면 그 숫자에 닿는 경로가 있는지 확인할 것** |
| 확인이 오래 걸리는 기능 | 위를 고쳐도 다리가 부러지려면 물기를 네 번 맞아야 해서 한 번 보는 데 십수 초가 걸렸다. **만든 사람이 확인하기 어려운 기능은 있어도 없는 것과 같다** — 디버그 키(F4)를 먼저 만들 것 |
| ★ 맥락 조건이 **거의 항상 참**일 때 | 「달리는 중이면 대시 공격」으로 두었더니 이동을 거의 항상 하고 있어서 **평타가 안 나왔다.** 맥락으로 분기할 때는 그 맥락이 얼마나 자주 참인지를 봐야 한다 — 자주 참이면 그게 곧 기본값이 된다 |
| ★ 시트 크기를 바꾸면 겹치는 시트도 같이 | 몸 시트에 행을 하나 더했더니 팔 레이어 4장이 칸 수가 안 맞게 되었다. **겹쳐 그리는 시트는 크기·칸이 1:1 이어야 한다** — 생성 스크립트를 멱등으로 만들어 둔 덕에 다시 돌리는 것으로 끝났다 |
| ★ 좌표계의 **의미**가 바뀔 때 | 벨트스크롤(`y` = 깊이)에서 플랫포머(`y` = 높이)로 가면 `y` 를 쓰는 모든 곳의 뜻이 동시에 바뀐다. 인자(`moveY` / `dirY`)를 **지워서** 컴파일러가 전부 찾게 했다 — 「의미만 바뀌고 타입은 같은」 변경은 눈으로 못 찾는다 |
| 공유 구조체에 필드 추가 | `AttackData` 를 플레이어와 적이 함께 쓰므로, 필드를 **맨 앞에** 추가하면 위치 초기화를 쓰는 적 데이터가 전부 깨진다(다행히 컴파일 에러로 잡힌다) |
| ★ PowerShell 변수명은 대소문자 구분 없음 | `$FRONT`(색)와 `$front`(비트맵)가 **같은 변수**여서 색이 비트맵으로 덮여썼다. `$colArmFront` / `$bmArmFront` 처럼 접두어로 나눌 것 |
| PowerShell 에서 `GetPixel` 루프 | 384x576 = 22만 번이면 끝나지 않는다. `LockBits` + `Marshal.Copy` 로 바이트 배열을 한 번에 읽을 것 |
| ★ 없는 것은 지울 수 없다 | 「잘린 팔을 지우자」로 시작했는데 몸 시트에는 **팔이 애초에 안 그려져 있었다.** 통짜 실루엣에서 부위를 빼려면 먼저 부위를 **레이어로 더해야** 한다. 에셋을 먼저 열어 볼 것 |
| 겹쳐 그릴 때 「칠해도 되는 곳」 | 팔을 덧칠했더니 칼날을 덮었고, 상처를 덮어썼더니 **얼굴에 피가 묻었다.** 예외를 하나씩 잡지 말고 규칙으로 쓸 것 — 팔은 *투명한 곳에만*, 상처는 *몸의 색 위에만* |
| ★★ 이미 뒤집힌 것을 또 뒤집기 | `Box()` 가 `facing` 으로 상자를 통째로 미러링하므로 **「앞팔 = 오른팔」은 facing 과 무관하게 고정**이다. 그런데 `PickHit` 이 `facing` 으로 앞/뒤 팔을 한 번 더 골라서 **두 번 뒤집혀 제자리로** 돌아왔다 → 오른팔이 잘린 채 돌아서도 팔이 그 자리에 그대로 있었고, 판정은 반대쪽 팔이 막았다. **몸이 이미 뒤집어 준 것을 코드가 또 뒤집지 말 것** (`Part_FrontArm` / `Part_BackArm` 한 곳에서 정한다) |
| ★ 주석으로 「맞춰 쓰라」고 적는 것은 맞춘 것이 아니다 | 위 버그를 스프라이트 쪽에 **베껴 쓰면서** 「`PickHit` 과 같은 규칙이어야 한다」는 주석까지 달았다. 규칙은 이미 틀려 있었고, 베끼는 순간 틀린 규칙이 두 벌이 되었다. 같은 규칙은 **같은 자리**에 둘 것 |
| 위치(앞/뒤)와 정체(좌/우)를 섞기 | 「오른손 무기를 떨군다」는 **정체**로 판정해야 한다 — 돌아섰다고 무기가 다른 손으로 옮겨가면 안 된다. 「어느 팔이 몸통을 가리는가」는 **위치**다. 둘을 하나의 이름으로 쓰면 반드시 한쪽이 틀린다 |

**「정수로 맞춘다」는 픽셀아트의 반복 규칙**: 화면 확대(정수 배율) / 폰트 좌표 / 카메라 흔들림 오프셋 / 스프라이트 위치.

## 8.5 엔진과 게임의 경계 — design.md §9

> 유용한 기능은 **엔진**에, 게임 코드는 **조립만**. 다만 경계선을 어디에 긋느냐가 전부다.

```
너무 늦게 긋는다  ->  PlayScene.cpp 가 1,700줄이 된다
너무 일찍 긋는다  ->  아무도 안 쓰는 일반성이 쌓인다   ← 이쪽이 더 나쁘다 (지우기 어렵다)
```

★ **규칙: 두 번째 사용자가 생겼을 때 올린다.** 셀 수 있는 사실이라 판단이 흔들리지 않는다.
이미 그렇게 움직여 왔다 — `AttackData` / `MakeAttackBox` / `SlideDecaying` /
`Renderer::DebugDraw` / `Scene::Resume` 전부 **필요해진 뒤에** 올렸다.

★ **리팩터링은 기능 추가에 태운다.** 「정리만 하는 큰 작업」을 따로 하지 않는다 —
아래 §9 가 기록하듯 이 프로젝트의 최악 버그 2건이 전부 큰 리팩터링에서 나왔다.
6-c 가 필요로 하는 물리를 6-c 에서, 6-e 가 필요로 하는 카메라 추적을 6-e 에서 올린다.

**아직 엔진에 없고 곧 필요한 것**: `Rigidbody2D`(중력·속도) / `Collider2D`(지형) — 6-c.
**있지만 게임 코드가 직접 쓰는 것**: `Sprites().Draw(…인자 8개)` — 두 곳에서 반복 중.

## 9. 리팩터링 시 체크리스트

2배속 버그와 애니메이션 정지 버그가 **둘 다 큰 리팩터링에서 한 줄이 어긋난** 경우였다.
문법이 멀쩡해 컴파일러가 못 잡는다.

> **옮기기 전후의 호출 목록을 `Grep` 으로 비교한다.**
>
> ```
> before:  Play / Tick / Finished / SourceRect
> after:   Play / Finished / SourceRect      ← Tick 이 없다
> ```
>
> 30초면 잡힌다. 빌드 성공만 보고 넘어가지 말 것.

### ★★ 9.1 「진짜 답」을 새로 만들 때 — 가장 자주 나는 사고

이 프로젝트에서 **하나 고치면 다른 게 터지는** 일의 원인은 거의 전부 같다.
**파생된 답을 새로 만들면서 옛 출처를 그대로 두는 것**이다.

| 새로 만든 것 | 그대로 남은 옛 출처 | 터진 것 |
|---|---|---|
| `Part_FrontArm` | `facing` 으로 직접 계산 | 돌아서도 잘린 팔이 안 따라옴 |
| `BodyComponent::MoveX` | `tr.x` 직접 대입 (3곳) | 구르기·넉백이 벽을 통과 |
| `PostureClip()` | `Prone() ? … : …` (5곳) | 웅크렸는데 선 그림 |
| `Crouched()` | `m_crouching` / `CrouchHeld()` (4곳) | 이동이 빠름 · 공격하면 섬 |
| `CurrentPosture()` (자세 3종) | `Prone() ? … : …` 2분기 (4곳) | 웅크린 물기가 **제 머리 위**로 나감 · 엎드려 Ctrl 누르면 속도 **두 번** 깎임 |
| `SetPosture(Posture)` | `SetCrouching(bool)` | **bool 은 세 번째 값을 말할 수 없다** — 엎드린 몸이 「선 크기」로 남았고, 적은 아예 자세를 안 알려 주고 있었다 |

**왜 못 잡는가**: 타입이 같다. `bool` → `bool`, `float` → `float`.
컴파일도 되고 동작도 한다. **낡은 질문에 정확히 답할 뿐이다.**
그래서 테스트해도 「그 상황」을 밟기 전까지는 안 보인다.

> ### 규칙 — 파생을 만들면 **원본의 이름을 바꾼다**
>
> ```
> m_crouching  →  m_crouchHeld      (이건 입력이지 자세가 아니다)
> ```
>
> 이름이 바뀌는 순간 옛 사용처가 **전부 컴파일 에러**가 된다.
> 하나씩 「이건 원본을 물어야 하나, 파생을 물어야 하나」를 정하게 되므로
> **빠뜨릴 수가 없다.**
>
> 원본을 아예 지울 수 있으면 지운다(`Player::x/y/facing`, `Enemy` 구조체가
> 그랬다). 지울 수 없을 때 쓰는 것이 이름 바꾸기다.

★ 자매 규칙: **경우가 둘에서 셋이 되면 `? :` 를 `switch` 로 바꾼다.**
`Prone() ? A : B` 는 자세가 셋이 된 순간 **웅크리기를 조용히 삼킨다.**
`switch (Posture)` 로 쓰면 새 값을 더할 때 컴파일러가 빠진 `case` 를 짚어 준다.

★ 함께 볼 것: **이름에 「무엇인가」가 아니라 「어디서 왔는가」를 넣는다.**
`m_crouchHeld`(입력) / `Crouched()`(자세) 처럼 나눠 두면
읽는 쪽이 둘을 헷갈릴 수 없다.
