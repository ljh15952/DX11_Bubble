용에게 마을을 잃은 아이가 복수를 위해 나아가지만, 끝에서 **용도 피해자였다**는 것을 알게 되는
고정화면 2D 소울라이크 액션.

## 1. 핵심 컨셉

### 1.1 게임의 정체성 — 지문(指輪)

이 게임의 모든 지문은 **능력이 아니라 인식을 바꾼다.** 세상은 그대로인데, 내가 볼 수 있는 것이 늘어난다.

| 지문 | 보이게 되는 것 | 입수 |
|---|---|---|
| 初心者の指輪 | 적의 공격 예고(`!`) | 최초 |
| 蛍の指輪 | 어둠 속 | 보스 전리품 |
| 竜の指輪 | 용의 말 | 종반 |
| 亡者の指輪 *(제안)* | 그 방에서 과거에 일어난 일의 환영 | 미정 |
| 真実の指輪 *(제안)* | 적의 약점 부위와 남은 부위 HP | 미정 |

이 게임의 진실은 **최면술로 가려져 있다.** 용은 원래 적이 아니었다.

> **지문 = 가려진 진실을 벗기는 도구**

기획 전체가 이 한 줄로 묶인다. 새 아이템을 추가할 때 이 규칙에 맞는지 먼저 확인한다.

### 1.2 지문 슬롯 제한 — **확정**

**장착 슬롯은 2개.** 모든 지문이 「무엇을 포기할 것인가」의 선택이 된다.

> 어두운 동굴에서 강적을 만났다 → 蛍(밝기)을 뺄까, 初心者(공격 예고)를 뺄까?

蛍の指輪을 장착하지 않으면 횃불을 들어야 하고, 횃불은 한 손을 차지해 **양손 무기를 쓸 수 없다.**
이 기회비용이 지문 시스템의 핵심이다.

## 2. 스토리

### 2.1 서장

부모가 다급하게 아이를 깨우며 시작한다. 마을은 용의 습격을 받아 모두 도망치는 상황.
부모는 아이를 지키다 희생되고, 아이는 마을의 **유일한 생존자**가 되어 복수를 결심한다.

### 2.2 종반 — 입장의 역전

주인공이 **용의 마을을 습격한다.** 게임 시작과 정확히 반대 위치에 서게 된다.
이때 플레이어가 스스로 그 대칭을 알아채도록 연출한다. 설명하지 않는다.

### 2.3 결말

竜の指輪을 장착하고 마지막 용을 쓰러뜨리면, 죽기 직전 **최면술이 풀리며 흑막을 알려준다.**
진짜 흑막과 싸우게 되고, 쓰러뜨리면 모든 용에게 걸려 있던 최면이 풀린다.

다 끝났다고 생각한 순간 **아기 용이 다가온다.** 앞으로 사이좋게 지낼 가능성을 보여주며 끝.

## 3. 시스템

### 3.1 전투 — 스태미나제 **확정**

다크소울식 완전 스태미나제. **공격·구르기·가드가 전부 스태미나를 소모한다.**

| 항목 | 규칙 |
|---|---|
| 소모 | 공격 / 구르기 / 가드 시 피격 |
| 회복 | 행동 후 일정 시간(회복 지연) 뒤부터 자동 회복 |
| 고갈 | 회복될 때까지 아무 행동도 못 함 = 최대 위기 |
| 가드 | 스태미나로 데미지를 받아냄. 고갈되면 가드 붕괴 |

전투의 핵심 질문은 **「지금 둘러야 하나, 참아야 하나」**.
욕심내서 한 대 더 치면 구를 스태미나가 없다 — 이 긴장이 게임 전체의 리듬이 된다.

> 적 패턴은 **스태미나 경제를 기준으로 설계한다.**
> 「연속 3타 후 빈틈」이 아니라 「연속 3타를 다 구르면 스태미나가 바닥난다」로 설계할 것.

### 3.1.1 강인도(poise) — 경직을 데이터가 정한다 **확정**

맞았을 때 경직에 걸리는지 아닌지를 코드가 아니라 **숫자가 결정한다.**

```
방어구의 강인도(poise)  >=  적 공격의 충격력(impact)   →   데미지만. 자리에서 버틴다
방어구의 강인도(poise)  <   적 공격의 충격력(impact)   →   경직 + 넉백 + 피격 무적
```

**Why:** 「경직을 둘까 말까」는 게임 전체를 가르는 질문인데, 코드로 고정하면
그 답이 하나뿐이 된다. 숫자로 두면 **방어구 하나하나가 다른 게임**을 만든다.
상태 머신 원칙(「상태는 안 늘어나고, 다양성은 데이터에서」)의 또 하나의 적용이다.

★ **버티기는 안전한 것이 아니라 다른 지불 방식이다.**

| | 회피 | 버티기 |
|---|---|---|
| 지불 수단 | **스태미나** | **HP** |
| 요구 | 타이밍 | 장비 |
| 실패 시 | 경직 + 데미지 | (없음. 확정 데미지) |

이 대비가 방어구를 「강함」이 아니라 **선택**으로 만든다. 그래서 미결정이었던
「방어구: 무게 → 구르기 속도 연동?」의 답도 여기서 나온다:

```
가벼운 방어구   poise 낮음 → 경직 O   구르기 빠름   →  「흘려서 산다」
무거운 방어구   poise 높음 → 경직 X   구르기 느림   →  「버텨서 산다」
```

지문 슬롯 2개와 **같은 종류의 기회비용**이다.

**방식은 문턱(threshold)** — 단순 비교다(다크소울 1식). 게이지가 깎이고 회복되는
소모 방식(다크소울 3식)은 「3타 중 2타는 버티고 3타에 무너진다」를 만들 수 있지만,
문턱이 「내 방어구로 이 적을 버틸 수 있나」를 한 번의 실험으로 학습시킨다.
나중에 바꾸려면 위의 비교 한 줄이 게이지 감산으로 바뀔 뿐이다.

> **충격력(impact)은 데미지와 다른 숫자로 둔다.** 합치면 「약하지만 크게 휘청이게
> 하는 공격」(방패 밀치기 같은 것)을 만들 수 없다.

### 적도 강인도를 가진다 **확정** (2026-09-10)

같은 규칙이 양쪽에 걸린다. 값의 출처만 다르다 —
플레이어는 **방어구**에서, 적은 **종류마다 타고난 값**에서.

★ **이것이 예고(`!`)에 두 번째 용도를 준다.**

```
적의 예고가 뜬다
   ├─ 구른다      = 흘린다   (무적 프레임)
   └─ 강하게 친다 = 끊는다   (강인도 돌파 → 공격 취소)
```

단검의 impact 는 light 14 / crouch 14 / running 16 / thrust 18 이고
잡몹의 강인도는 **15** 다. 그래서:

| 끊을 수 있는가 | 공격 | 스태미나 |
|---|---|---|
| ✗ | LIGHT · CROUCH | 28 · 26 |
| ✓ | RUN · THRUST | **34 · 34** |

★ **끊을 수 있는 둘이 정확히 비싼 둘이다.**
「적을 끊으려면 스태미나를 더 낸다」가 데이터만으로 성립한다.
그리고 THRUST 는 1타를 맞춰야 나오므로 **끊으려면 먼저 한 대 넣어야 한다.**

13 이면 전부 끊겨 선택이 사라지고, 20 이면 아무것도 못 끊어 시스템이 죽는다.
보스는 훨씬 높게 두어 「끊을 수 없는 적」을 만든다.

**무한 경직 방지는 양쪽이 다른 방식이다.**

| | 방식 | 왜 |
|---|---|---|
| 플레이어 | **피격 무적**(24틱 > 경직 18틱) | 억울한 죽음을 막는다 |
| 적 | **경직 내성**(30틱 > 경직 16틱) | 무적을 주면 콤보가 아예 안 들어간다 |

둘 다 「회복 직후가 안전해야 루프가 안 생긴다」는 같은 원리다.

### 3.1.2 무적 프레임의 처리 방식 **확정**

구르기의 무적 구간이 적 공격의 지속 구간과 겹쳤을 때:

> **무적인 틱은 없었던 일로 한다.** 그 휘두르기를 소진시키지 않는다 —
> 무적이 풀린 다음 틱에 지속 구간이 남아 있으면 **그때 맞는다.**

「무적 프레임」이 문자 그대로 동작하는 쪽을 택했다. 한 틱만 스쳐도 그 공격을
통째로 흘리는 방식(관대함)은 **별개 규칙**이고, 그건 나중에 **패링(parry)** 을
만들 때 쓸 개념이다. 지금 섞으면 둘 다 애매해진다.

무적 12틱 > 지속 4틱 이므로 타이밍만 맞으면 완전 회피가 된다.

### 3.1.3 스턴락 방지 **확정**

경직 중에 또 맞으면 경직이 0부터 다시 시작한다. 적이 두 마리면 영원히 못 움직인다.
이것이 스턴락이고, 「억울하게 죽었다」는 감각의 원인이다.

> **피격 무적 길이 > 경직 길이.** 경직이 풀리고 **나서도 조금 더** 안전해야 한다.
> 같게 두면 경직이 풀리는 그 틱에 다시 맞는다.

★ 무적이 두 종류가 되고, **성격이 다르다.**

| | 구르기 무적 | 피격 무적 |
|---|---|---|
| 누가 주는가 | 플레이어가 **벌어낸다**(스태미나 + 타이밍) | 게임이 **준다** |
| 정체 | 게임 디자인 — 재미를 만든다 | 게임 공학 — 불공평을 막는다 |
| 표현 | 색 (푸르게) | 깜빡임 |

★ 피격 무적은 **경직의 부속품**이다. 강인도로 버텨내면 못 움직이는 구간이
없으므로 스턴락 위험도 없고, 그래서 피격 무적도 주지 않는다.

### 3.2 부위 파괴 — 핵심 시스템 **확정**

**적도 플레이어도 부위별 HP를 가진다.** 이 게임의 최대 차별점.

| 부위 | 파괴 시 |
|---|---|
| 다리 | 이동 불가. 적은 **기어서 쫓아오고**, 플레이어는 **구르기를 잃는다** |
| 왼팔 / 오른팔 | **그 손의 무기를 떨군다.** 잘리기 전까지는 몸통의 완충재 |
| 머리 | **격파** (HP 가 몸통의 1/5) |
| 몸통 / 코어 | 격파 |

전술적 선택이 매 전투마다 생긴다 — 빠른 적은 다리, 강타형 적은 팔.

> 부위 목록·절단·완충재 규칙은 **§3.2.2**, 몸 UI 는 **§3.2.3** 참조.
> 플레이어에게도 적용된다는 것이 2026-09-10 의 결정이다.

### 머리 = 즉사 **확정** (2026-09-09 변경)

원안은 「시야 상실 → 소리로만 쫓는다」였다. **폐기한다.**

**Why:** 소리 전파와 수색 AI 가 필요해 비용이 다른 부위 파괴 전부를 합친 것보다 크다.
그리고 즉사가 **보상으로 더 명확하다** — 「머리 HP 는 몸통의 1/5 이지만 상자가
작고 높다」는 위험/보상 관계가 설명 없이 전달된다.

이 결정으로 §1.1 의 「머리 파괴의 대칭성 — 蛍の指輪을 빼면 *내가* 어둠 속에 있고,
머리를 부수면 *적이* 어둠 속에 있다」는 **아이디어는 폐기된다.** 아까운 대칭이지만
그 대칭을 위해 청각 시스템 하나를 만들 값은 아니다.

**How to apply:** 부위 파괴 처리에서 `머리 또는 몸통 → 격파`. 다리는 그대로
「이동 불가」다. 「다리만 베었는데 격파는 비현실적」이라는 출발점은 유지된다.

> ★ 그리고 이 결정으로 **판정 상자만으로 조합이 완성됐다.**
> 다리를 부수면 적이 엎드리고, 엎드린 자세의 머리 상자가 앞으로 튀어나오면서
> 기본 공격 높이에 들어온다.
>
> ```
> 다리(40) 4방 → 기어옴 → 머리(20) 2방 = 6방
> 몸통 정면                            = 9방
> ```
>
> 「부위를 노리면 빨리 죽는다」가 새 코드 없이 데이터에서 나왔다.
> 다만 엎드린 적도 물어뜯으므로(사거리 짧고 후딜 길게) 리스크는 남는다 —
> 「다리를 부수면 완전 무력화」로 만들면 항상 다리부터 노리는 것이 정답이 되어
> 이 절의 전술적 선택이 사라진다.

### 3.2.1 무기 모션이 노리는 부위를 결정한다 **확정**

무기마다 모션이 다르고, **모션에 따라 닿는 부위가 다르다.**

| 모션 예 | 히트박스 높이 | 주로 닿는 부위 |
|---|---|---|
| 서서 약공격 | 몸통 높이 | 몸통 |
| **웅크려 공격** | 발밑 근처 | **다리** |
| 위로 베기 / 찌르기 | 머리 높이 | 머리 |
| 대검 내려찍기 | 넓게 전부 | 겹침 면적이 큰 쪽 |

**Why:** 부위 파괴가 「우연히 어디가 맞았나」가 아니라 **플레이어가 조준하는 행위**가 되어야
전술이 생긴다. 「다리를 봉쇄하려면 웅크려서 쳐라」가 성립하는 순간
기획서 3.2 의 부위 파괴가 실제로 게임이 된다.

**How to apply:** 코드는 이미 준비되어 있다. `AttackData.heightFromFoot` 하나로
닿는 부위가 바뀐다(겹침 면적으로 부위를 고르므로). 남은 것은 **데이터 구조**다.

```
무기 하나  =  공격 여러 개(무브셋)
    dagger.light        heightFromFoot 34   → 몸통
    dagger.crouch       heightFromFoot 10   → 다리
    dagger.thrust       heightFromFoot 48   → 머리
```

### 3.2.1.1 버튼은 **손**을 가리킨다 **확정** (2026-09-15)

| 입력 | 뜻 |
|---|---|
| 좌클릭 / 패드 X | **왼손** |
| 우클릭 / 패드 Y | **오른손** |

★ 버튼에 **행동**이 아니라 **손**을 담는다. 무엇이 나갈지는
**그 손에 무엇이 들려 있는지**가 정한다:

| 그 손의 상태 | 결과 |
|---|---|
| 무기 | 무브셋(아래 표) |
| 빈손 · 잘림 | **물기** |

★★ 전에는 「좌클릭 = 공격 / 우클릭 = 물기」였다. 그러면 무기를 어느 손에
들었든 조작이 같아서 **손이 둘이라는 사실이 조작에 안 나타났다** —
§3.10 의 슬롯 구조가 화면에만 있고 손끝에는 없었던 셈이다.

이 변경으로 **규칙이 줄었다**:

- 물기는 **전용 버튼이 아니라 상태**가 되었다 — 휘두를 것이 없으면 남는 것은
  이빨뿐이다(§3.2.2.1). 특수 분기가 사라졌다.
- `CanAttack()`(「공격할 수 있는가」)이 통째로 사라졌다. **못 하는 경우가 없다.**
- ~~줍기가 **누른 손**에 든다~~ → **철회** (2026-09-16, §4.0.5).
  무기를 밟고 선 동안 손이 통째로 막혔다. 줍기는 `E` 로 옮기고 손 선택은
  **8단계 장비 화면**으로 미룬다. 손 버튼은 **언제나 손**이 되었다.

※ 양손에 무기를 드는 것은 8단계(인벤토리)의 몫이다. 그때는 두 버튼이
각각 다른 무브셋을 내게 되고, 지금 구조가 그대로 확장된다.

### 3.2.1.2 숫자는 `weapons.json` 으로 나갔다 **확정** (2026-09-15)

무브셋 9종의 프레임 데이터·상자·데미지가 `assets/data/weapons.json` 에 있다.
**F6** 으로 다시 읽으므로 빌드 없이 밸런스를 만진다.

★ **C++ 상수는 사라진 것이 아니라 「기본값」이 되었다.**

| | |
|---|---|
| 파일이 없다 | 기본값으로 돈다 |
| 키를 몇 개만 적었다 | 나머지는 기본값 |
| 오타가 났다 | **옛 값 그대로** + 로그 (게임은 안 죽는다) |

「고치다 오타가 나면 게임이 죽는다」가 되면 아무도 핫 리로드를 안 쓴다 —
리로드의 값어치는 **틀려도 안전하다**는 데서 나온다.

★ **JSON 에는 주석을 못 단다.** 그래서 숫자만 파일로 보내고
**「왜 그 값인지」는 C++ 주석에 남긴다.** 상수를 지우지 않은 진짜 이유다.

★ 읽을 때 **문서에 적어 둔 함정을 코드가 검사한다**(경고만, 막지는 않는다):

- `frames × ticksPerFrame == TotalTicks` — 아니면 그림과 판정이 어긋난다
- `startup % ticksPerFrame == 0` — 아니면 타격 프레임이 안 맞는다

숫자를 파일로 뺀 순간 이 규칙을 **어기기가 훨씬 쉬워졌다**(빌드도 안 하니까).
그래서 읽을 때 봐 준다.

※ `name` 은 덮어쓰지 않는다 — `const char*` 라 수명 문제가 생기고,
무엇보다 **이름은 조정하는 값이 아니라 식별자**다. 새 무기는 8단계의 몫이다.

**입력 맥락이 어느 공격인지 결정한다.**

#### 높이는 **중심이 아니라 띠**다 **확정** (2026-09-16)

| 공격 | 띠(발끝 기준) | 닿는 곳 |
|---|---|---|
| light · dash | **26 ~ 36** | 선 적의 몸통만 |
| crouch | 2 ~ 18 | 다리 · 낮춘 적 |
| thrust | 37 ~ 59 | 머리 |
| jump | -9 ~ 21 | 위에서 머리 · 낮춘 적 |

★ light 는 원래 **높이 24(22~46)** 였다. 「몸통을 노린다」고 적어 두었지만
실제로는 선 적의 **머리(37~55)까지 물었고**, 무엇보다 **몸을 낮춘 적의
머리(11~25)를 3픽셀 스쳐 즉사**시켰다 — 평타로 목이 날아갔다.

이것은 §3.9 에서 고친 「엎드린 플레이어가 중단에 머리를 맞던」 버그의
**거울상**이다. 적의 휘두르기만 띠로 좁히고 플레이어 쪽은 안 좁혔다.

★★ **닿는 부위는 중심값이 아니라 띠 전체가 정한다.** 그래서 문서에도
중심값 대신 **범위**를 적는다.

★ 결과: **덤벼들며 무는 적에게는 평타가 빗나간다.** 그때는 웅크려 베거나
뛰어올라 찍어야 한다 — 적이 자세로 방어하듯 플레이어도 자세로 답한다.

| 상태 / 입력 | 나가는 공격 | 닿는 부위 |
|---|---|---|
| 서서 / **걸으며** + 공격 | light | 몸통 |
| **Ctrl** + 공격 | crouch | **다리** (+ 중단 회피) |

★ 웅크리면 **점프도 구르기도 못 한다.** 둘 다 땅을 박차는 전신 동작이다.
중단을 흘리는 대신 기동성을 통째로 내주는 것이 웅크리기의 값이고,
천장에 눌려 못 일어서는 자리는 **안전한 곳이 아니라 선택지가 없는 곳**이 된다.
| **구르기 직후** + 공격 | dash | 몸통 (길게 뻗는다) |
| 공격 중 + 공격 | 2타 = thrust | **머리** |
| **공중** + 공격 | jump | **머리** (위에서 찍는다) |

물기도 자세를 따라간다. **자기 머리 높이**로 물기 때문이다.

| 자세 | 무는 높이 | 사거리(몸 중심 기준) | 닿는 곳 |
|---|---|---|---|
| 서기 | 48 | 4 ~ 22 | 선 적의 **머리** = 즉사 |
| 웅크리기 | 20 | 4 ~ 22 | 몸통 · 다리 |
| 엎드리기 | 18 | **18 ~ 34** | 몸통 · 다리 |

★ 엎드린 사거리만 앞으로 밀려 있다. **엎드리면 머리가 앞으로 나가기**
때문이다(머리 상자 x 4~20). 몸 중심에서 재면 판정이 제 머리 위에 얹힌다.
**사거리는 몸 중심이 아니라 입에서 잰다.**

★ **「목을 물려면 일어서야 한다」가 좌표만으로 성립한다.**
웅크리기는 중단을 흘리는 대신 즉사를 노릴 수 없다 — 그 대가가 여기서 나온다.

### 선택 규칙 **확정** (2026-09-10 구현)

> **명시적 입력이 암묵적 맥락을 이긴다.** 그다음은 암묵적 맥락끼리 구체적인 것부터.

```
⓪ 공중이다             -> jump       (땅의 선택지는 전부 「발이 땅에 있다」가 전제다)
① Ctrl 을 누르고 있다   -> crouch     (지금 누르고 있는 것이 가장 최신 의도다)
② 공격 중이었다         -> 2타
③ 구르기 직후다         -> dash
④ 그 밖                 -> light
```

#### ③ 이 「달리는 중」에서 「구르기 직후」로 바뀌었다 **확정** (2026-09-14)

달리는 중으로 두었더니 **평타가 거의 안 나왔다.** 이동은 거의 항상 하고 있으므로
「기본 공격」이 기본이 아니게 되었고, 무브셋이 선택지가 아니라 사고가 되어 있었다.

구르기 뒤로 옮기면 **대가를 먼저 치른 사람만** 쓴다:

| | 스태미나 | 100 중 |
|---|---|---|
| 구르기 + dash | 30 + 34 | 64 |
| 거기서 thrust 까지 | +34 | **98** — 거의 전부 |

길게 뻗는 공격이 「굴러서 파고든 뒤」에 붙으므로 동작의 의미도 맞는다.
예약을 받는 시점도 공격 콤보와 **같은 모양**이다 — 「위험 구간이 끝난 뒤부터」:
공격은 active 뒤부터, 구르기는 **무적이 끝난 뒤부터**.

**웅크리기는 상태가 아니라 수식자(modifier)다.**

> ~~웅크린 자세의 **피격 판정**이 실제로 달라져야 할 때 상태로 승격하면 된다.~~
> **(2026-09-14 정정)** 그 시점이 왔는데, 막상 해 보니 **상태로 올리면 안 됐다.**
> 상태 머신은 한 번에 하나만 될 수 있는데 웅크리기는 **공격과 공존한다** —
> 웅크려 다리를 베는 것이 무브셋의 핵심이다.
> 달라지는 것은 상태가 아니라 **자세(Posture)** 였고, 그래서 판정 상자를 가진
> `PartsComponent` 에 `Stand / Crouch / Prone` 을 두었다.
>
> ★ 「조건이 흩어지면 상태로 승격한다」는 원칙은 맞지만, **승격 대상이
> 상태가 아닐 수도 있다.** 공존해야 하는 것은 상태가 될 수 없다.

※ `Ctrl` / 패드 `LB` 를 쓴다. 플랫포머가 되면서 ↓ 가 비었지만 유지한다(§3.8.3).

### 엎드리기는 「중단 공격을 흘린다」 **확정** (2026-09-14)

  ★ 36
    중단 띠 (26~36)            팔 20~36 · 몸통 18~37 에 닿는다
  ★ 26
    ~ 25      엎드린 몸 전체   ← 닿으면 엎드리기가 의미를 잃는다

★ **특수 규칙이 아니라 좌표다.** 「엎드리면 회피」라는 상태 검사가 어디에도 없다.

### 웅크리기도 같은 원리 **확정** (2026-09-14)

|---|---|---|
| 서기 | 55 | 맞는다 (팔 → 몸통) |

머리는 그대로 두고 몸만 접는 그림을 그리면 둘이 같은 숫자에서 만난다.

★ 대신 **무적은 아니다.** 상대가 엎드린 것을 본 적은 **물기**(발끝 4~20)로
바꾼다. 물기는 사거리가 짧아 더 붙어야 하므로, 엎드리기는

### 잡몹은 두 공격을 **번갈아** 낸다 **확정** (2026-09-14)

| | 예고 | 높이 | 데미지 | 대처 |
|---|---|---|---|---|
| SWING | 24틱 | 중단 26~36 | 18 | 구르거나 **엎드려** 흘린다 |
| BITE | 18틱 | 하단 4~20 | 10 | 엎드리면 못 피한다. 구른다 |

★ **번갈아 내지 않으면 다리 파괴가 도달할 수 없는 기능이 된다.**
중단만 나오면 플레이어의 다리(발끝 0~18)에 닿는 공격이 하나도 없다.
실제로 그랬다 — 부위 5개 중 다리만 아무도 건드릴 수 없는 숫자였다.

있다. 「하나를 피하는 자세가 다른 하나에는 약하다」가 §3.1 의 리듬을 만든다.

### 무브셋이 만들어낸 것

★ **「머리를 노리려면 콤보를 성공시켜야 한다」가 데이터만으로 성립했다.**
머리는 즉사(§3.2)이고 thrust 는 1타를 낸 뒤에만 나오므로,
새 규칙을 한 줄도 안 쓰고 리스크/보상이 생긴다.

★ **스태미나 경제(§3.1)와 맞물린다.**
`light(28) + thrust(34) = 62`. 100 중 62를 쓰면 38 이 남고 구르기는 30 이므로,
**콤보 뒤에는 한 번밖에 못 구른다.** 「욕심내서 2타를 넣을까, 남겨서 구를까」가
매 순간의 질문이 된다 — §3.1 이 요구한 바로 그 긴장이다.

★ **웅크리기는 느리다**(이동 0.45배). 조준의 대가다.
「다리를 봉쇄하려면 멈춰서 노려야 한다」가 이동 속도 한 줄로 만들어진다.

### 선택 사항 — 프레임별 히트박스 (스윙 궤적)

지금은 active 구간 내내 히트박스가 **한 자리에 고정**되어 있다.
실제 칼은 호를 그리므로, 프레임마다 히트박스를 다르게 두면 훨씬 자연스럽다.

```
t8   히트박스 (높이 48)  ← 위에서
t9   히트박스 (높이 32)  ← 중간
t10  히트박스 (높이 16)  ← 아래로
```

이렇게 하면 **닿는 타이밍에 따라 맞는 부위가 달라진다.** 격투게임이 실제로 쓰는 방식이다.
데이터가 늘어나므로 무브셋 구조가 정착된 뒤에 검토한다.

### 3.3 성장 — 3단계 **확정**

스토리 분기점에서만 변한다. **강화가 아니라 트레이드오프.**

| 단계 | 얻는 것 | 잃는 것 |
|---|---|---|
| 아이 | 몸이 작아 구르기가 빠르고 피격 판정이 작다 | 무거운 무기를 못 든다 |
| 소년 | 균형 | — |
| 청년 | 대형 무기, 높은 공격력 | 구르기가 느리고 몸집이 크다 |

「어릴 때가 오히려 피하기 쉬웠다」— 성장을 **상실을 동반한 변화**로 만든다. 복수극의 주제와 맞다.

> 3단계로 제한하는 이유는 **스프라이트 비용**이다. 나이별로 애니메이션 한 벌이 통째로 늘어난다.

### 3.4 주인공 — 1명 **확정**

스타팅 캐릭터 복수안은 채택하지 않는다. 주인공은 **「마을의 유일한 생존자인 아이」 한 명**이다.
「유일한 생존자」라는 서사가 이 게임의 출발점이므로 이것을 우선한다.

*(선택안: 「도망칠 때 무엇을 집어 들었는가」로 시작 무기만 분기시키면 리플레이 가치를 확보할 수 있다. 보류)*

### 3.5 기도 포인트 (세이브)

기도하는 곳에서 기도하면:

- 세이브
- HP / MP 회복
- 기도 포인트 간 텔레포트

**기도의 말이 진행도에 따라 바뀐다.** 구현은 문자열 테이블 하나지만 효과가 크다.

```
서장   "아버지, 어머니… 무서워요."
중반   "반드시 갚아주겠습니다."
종반   "……제가 틀렸던 걸까요."
```

플레이어는 같은 장소에서 같은 행동을 반복하는데, **자기 캐릭터가 변해가는 것을 문장으로 목격**한다.

> **미결정**: 기도하면 적이 부활하는가? (부활 → 파밍 가능·긴장감 / 비부활 → 탐험이 편함)

### 3.6 사망

`You died` 대신, 부활하면서 **멋진 대사**가 나온다 (「할 일을 해라」 같은 톤).

**한 줄 고정이 아니라 테이블로 둔다.** 진행도별 또는 사인(死因)별로 다른 대사.
시스템 비용은 같은데 플레이어가 「어, 아까랑 다르네?」를 발견하는 순간이 생긴다.

> **대사 테이블은 보류** (2026-09-10). 폐기가 아니다.
> BitmapFont 가 ASCII 전용이라 한국어·일본어 대사를 화면에 쓸 수 없다
> (§6.5 의 「런타임 글리프 아틀라스」가 먼저 필요하다).
> 지금은 `DeathScene` 의 문자열 한 줄이므로, 폰트가 생기면 그 자리에 테이블을 끼운다.

### 3.6.1 죽으면 무엇이 되돌아가는가 **확정**

> **죽었을 때 무엇이 되돌아가고 무엇이 남는가 — 그것이 이 게임이 무슨 게임인지를 정한다.**

| | 되돌아간다 | 남는다 |
|---|---|---|
| 플레이어 HP · 스태미나 · 위치 · 상태 | ✓ | |
| **적** (부위 HP 포함) | **✓ 되살아난다** | |
| **땅에 떨어진 무기** | | **✓** (§3.2.2.1) |
| 무기를 어느 손에 들었는가 | | ✓ |
| 열어둔 문 · 얻은 아이템 | | ✓ (7단계) |

**Why:** 전부 되돌리면 벌이 너무 크고, 아무것도 안 되돌리면 죽음이 무의미해진다.
「적은 되살아나지만 열어둔 문은 열린 채」가 소울류의 리듬 그 자체다.
적이 되살아나야 §3.1 의 스태미나 경제가 매번 다시 시험된다.

**How to apply:** `PlayScene::Respawn()` 하나가 이 표다.
★ **초기화(`Enter`)가 이 함수를 부른다.** 초기화와 부활은 같은 일이므로
두 벌로 만들면 반드시 어긋난다 — 필드를 추가할 때 한쪽만 고치게 되고
「두 번째 판부터 뭔가 이상하다」는 재현하기 어려운 버그가 된다.

부활 지점은 지금 방 하나뿐이라 시작 위치 고정이다.
§3.5 의 기도 포인트가 들어오면 그것이 부활 지점이 된다(7단계).
「기도하면 적이 부활하는가」는 이 결정에 따라 **부활한다**로 정리된다 —
죽음과 기도가 같은 규칙을 쓰는 편이 플레이어에게 설명하기 쉽다.

### 3.2.2 부위 목록과 절단 **확정** (2026-09-10)

부위를 **5개**로 나눈다. 팔이 좌우로 갈린다.

```
        ┌──────┐   머리      즉사
        ├──────┤
   왼팔─┤ 몸통 ├─오른팔      팔 : 그 손의 무기를 떨군다
        ├──┬───┤            몸통 : 즉사
        │  │   │   다리      다리 : 기어다닌다 (이동 대폭 감소 + 구르기 불가)
        └──┴───┘
```

**★ 플레이어도 같은 시스템을 쓴다.** 지금까지 부위 파괴는 적 전용이었지만,
플레이어에게도 붙인다. 컴포넌트로 만들어 두었으므로 **한 줄**로 붙는다 —
상속 계층이었다면 `Character` 를 뜯어고쳐야 했을 변경이다.

### ★ 팔은 몸통의 **완충재**다

이것이 이번 결정의 핵심이다.

```
중단(中段) 공격이 들어온다
        ↓
① 팔이 먼저 맞는다          (팔 HP 가 깎인다)
        ↓
② 팔이 잘린다               (그 손의 무기를 떨군다)
        ↓
③ 이제 몸통이 맞는다        (몸통이 부서지면 사망)
```

**Why:** 부위 파괴가 「어디를 노릴까」였는데, 여기서 **「무엇을 버릴까」**가 된다.
팔은 소모품이다 — 잘리면 무기를 잃지만 그만큼 몸통이 오래 버틴다.
§1.2 의 「모든 선택은 무엇을 포기할 것인가」가 전투 안으로 들어온 것이다.

그리고 **공격마다 팔에 들어가는 데미지가 다르다.** 같은 중단 공격이라도
베는 것과 찌르는 것이 팔을 잃는 속도를 다르게 만든다.

### 공격 높이(段)와 부위의 대응

`heightFromFoot` 이 이미 하고 있던 일에 이름을 붙인 것이다.

| 段 | 높이 | 닿는 부위 |
|---|---|---|
| 上段 | 높다 | 머리 |
| **中段** | 가운데 | **팔 → (잘리면) 몸통** |
| 下段 | 낮다 | 다리 |

### 부위 파괴의 결과

| 부위 | 적 | 플레이어 |
|---|---|---|
| 머리 | **즉사** | **즉사** |
| 몸통 | **즉사** | **즉사** |
| 왼팔 | 왼손 무기를 떨군다 | 왼손 무기를 떨군다 |
| 오른팔 | 오른손 무기를 떨군다 | 오른손 무기를 떨군다 |
| 다리 | 기어다닌다 | **쓰러져 기어간다 + 구르기 불가** (적과 같다) |

★ 다리 상실이 플레이어에게 가장 무섭다 — **구르기를 못 하면 §3.1 의
스태미나 경제가 통째로 무너진다.** 「흘려서 산다」가 사라지고 §3.1.1 의
「버텨서 산다」밖에 남지 않는다. 방어구 선택이 그 순간 결과를 바꾼다.

### 3.2.2.1 무기를 떨군다, 그리고 주우러 간다 **확정** (2026-09-10)

팔이 잘리면 **그 손의 무기가 땅에 떨어진다.** 사라지는 것이 아니라 **남는다.**

```
오른팔 절단 → 무기가 땅에 떨어진다 → 공격 불가
      ↓
  주우러 간다 (Space)  →  오른팔이 없으면 **왼손**에 든다
      ↓
  못 줍고 죽었다면?  →  무기는 그 자리에 그대로. 부활해서 다시 간다
```

★ 마지막 줄이 §3.6.1 의 「남는다」 칸에 **처음으로 진짜 내용**을 준다.
다크소울의 혈흔과 같은 구조이고, 구현은 **부활 처리가 무기를 건드리지 않는 것**뿐이다.
아무것도 안 하는 것이 기능이 되는 드문 경우다.

### ★ 팔을 다 잃으면 — 물기

무기를 쥐지 않는 공격을 하나 둔다. **팔이 없어도 나가고 언제든 쓸 수 있다.**

| | 값 | 왜 |
|---|---|---|
| 사거리 | 아주 짧다 | 목을 물려면 붙어야 한다 |
| 높이 | **머리** | 물기는 얼굴 높이다 → **즉사를 노린다** |
| 데미지 | 낮다 | 무기보다 나쁘다 |
| 스태미나 | 싸다 | 최후의 수단이 비싸면 안 된다 |
| 충격력 | 낮다 | 적을 끊지 못한다 |

★ **패배 직전이 가장 큰 보상을 노리는 순간**이 된다.
팔을 다 잃었을 때 남는 유일한 수가 「즉사를 노리는 도박」이라는 것 —
소울류의 리듬 그대로다.

**조작**: 좌클릭 = 보통 공격 / 우클릭 = 물기.
마우스가 여기서 처음 들어온다. 기존 키(Space·패드)는 그대로 남는다 —
`Input` 이 키가 아니라 **의도**로 번역하므로 장치를 늘려도 게임 코드가 안 바뀐다.

### 절단의 비용 — §8.1 이 예고한 그것

「팔이 잘린 상태」를 그려야 하므로 **단일 스프라이트로는 불가능하다.**
지금 `player.png` 는 7행 × 6프레임 = 42장의 통짜 그림이라,
팔·다리·머리 조합(최대 8가지)을 다 그리면 336장이 된다.

§8.1 이 권한 **하이브리드**로 간다:

```
몸통 + 다리   기존 통짜 애니메이션 (자세가 크게 바뀌므로)
팔 · 머리     겹쳐 그리는 별도 레이어  ->  잘리면 안 그린다
```

★ **컴포넌트가 이것을 공짜로 만든다.** `SpriteComponent` 를 여러 개 붙이면
그게 곧 레이어이고, 붙인 순서가 곧 그리는 순서다.

```
GameObject + [Sprite:몸통] [Sprite:왼팔] [Sprite:오른팔] [Sprite:머리]
```

`Require<SpriteComponent>()` 가 첫 번째만 돌려주므로 **이름표(tag)** 가 필요해진다.

### 3.2.3 몸 UI **확정**

화면 **좌하단**에 몸 그림을 두고, 부위 HP 가 낮을수록 그 부위가 붉어진다.
잘린 부위는 사라진다.

★ **HP 바는 없앤다.** 부위별 HP 가 생기면 「전체 HP」라는 숫자가 의미를 잃는다 —
몸통 20% 와 팔 20% 는 완전히 다른 상황인데 한 줄로는 구분되지 않는다.
그림이 곧 상태 표시다. (스태미나 바는 남는다 — 그건 여전히 하나의 값이다)

※ `BitmapFont` 가 ASCII 전용이라 부위 이름을 글자로 쓸 수 없다.
   **그림으로 가는 것이 제약을 피하는 것이 아니라 오히려 맞는 선택**이다.

## 3.7 내부 해상도 — 640×360 (×2 확대) **확정**

창은 1280×720 이지만, 게임은 **640×360 렌더 타겟에 그린 뒤 정수 2배로 확대**한다.

| 항목 | 값 |
|---|---|
| 내부 해상도 | 640 × 360 |
| 화면 확대 | ×2 (= 1280 × 720) |
| 캐릭터 크기 목표 | 48 ~ 64 px |

**Why:** 도트 게임에서 네이티브 1280×720 으로 그리면 스프라이트 하나에 드는 시간이
4~16 배가 되어 혼자서는 완성할 수 없다. 반대로 320×180 은 그림 작업은 가장 적지만
**부위별 파괴(팔·다리·머리)와 방어구 차이를 보여줄 수 없다.** 640×360 이 그 사이의 균형점이다.

**How to apply:** 좌표·이동 속도·히트박스 오프셋은 모두 640×360 기준으로 적는다.
1280×720 기준 숫자를 쓰면 안 된다. 확대는 마지막에 한 번만 일어난다.

구현 방식: 게임을 640×360 텍스처에 그리고(RTV), 그 텍스처를 화면에 ×2 로 그린다(SRV).
같은 텍스처에 RTV 와 SRV 를 둘 다 만드는 구조이며, **포스트 프로세싱(비네팅·색보정·블룸)의
토대가 그대로 생긴다.** 창 크기 변경도 레터박스로 자동 해결된다.

> 2026-09-07 시점: **결정만 되어 있고 아직 구현하지 않았다.** 현재 코드는 1280×720 네이티브다.

## 3.8 시점과 이동 — **플랫포머** **확정** (2026-09-10)

> **측면 뷰 + 중력 + 점프.**

### 문서에 있던 모순을 여기서 정리한다

`README.md` 와 `handoff.md` 는 처음부터 **「버블보블 같은 고정화면 2D」**라고 적어
두었는데, 아래 §4 는 참조로 **젤다 1편 / Binding of Isaac**(탑다운)을 들고 있었다.
그리고 코드는 그 사이에서 **벨트스크롤**(`y` = 깊이, 상하좌우 자유 이동)로 흘러갔다.

**세 개가 서로 다른 게임이었다.** 버블보블이 원래 의도이므로 그쪽으로 맞춘다.

### 무엇이 바뀌는가

| | 지금 (벨트스크롤) | 앞으로 (플랫포머) |
|---|---|---|
| `y` 의 의미 | **깊이** (화면 안쪽) | **높이** (중력이 당긴다) |
| 이동 | 상하좌우 자유 | **좌우만** + 점프 / 낙하 |
| 바닥 | 화면 아래쪽 clamp 하나 | **발판 사각형 목록** |
| 세로 위치 | 플레이어가 직접 정한다 | 중력과 점프가 정한다 |

**Why:** 「고정화면 한 장에서 싸운다」는 §4 의 결정과 플랫포머는 잘 맞는다 —
버블보블이 정확히 그 구조다. 그리고 부위 파괴(§3.2)는 **측면 뷰에서 훨씬 잘 읽힌다.**
머리·몸통·다리가 화면에서 위아래로 늘어서므로 「낮게 치면 다리」가 눈에 보인다.
탑다운이었다면 부위가 겹쳐 보여 이 게임의 핵심 시스템이 전달되지 않는다.

### 이미 만든 것 중 살아남는 것

거의 전부다. 이것이 상태 머신 · 프레임 데이터로 만들어 둔 값이다.

| 시스템 | |
|---|---|
| 상태 머신 · 프레임 데이터 · 스태미나 · 강인도 | 그대로 |
| 부위 파괴 · 판정 상자 | **오히려 더 잘 맞는다**(위 참조) |
| 무브셋 (`heightFromFoot`) | 그대로. 「발끝에서 몇 픽셀 위」가 실제 높이가 되어 의미가 더 명확해진다 |
| 사망 · 부활 · Scene 스택 | 그대로 |
| 카메라 | ~~여전히 불필요~~ → **필요하다.** 같은 날 §4 가 「넓은 맵 + 카메라 추적」으로 바뀌었다(6-e) |

### 바꿔야 하는 것

| 항목 | 내용 |
|---|---|
| 중력 · 점프 | 새 데이터(중력 가속도 · 점프 초속 · 최대 낙하 속도) |
| 지면 판정 | 발판 사각형 목록과의 충돌. 고정화면이므로 **타일맵은 불필요** — 사각형 몇 개면 된다 |
| 적 추격 | 2차원 접근 → **1차원 + 중력.** 낭떠러지에서 멈추는 판정이 필요해진다 |
| 넉백 | 수평 + 약간의 상승이 자연스럽다 |
| 구르기 | 지상에서만 |

### 3.8.1 점프는 **상태**다 **확정**

`PlayerState` 에 공중 상태를 추가한다. 상태가 **8개**가 된다
(Idle / Run / Attack / Roll / Exhausted / Hurt / Dead / **Jump**).

**Why:** 「상태는 6개에서 안 늘어난다」는 원칙의 진짜 내용은
**「조건이 여러 곳에 흩어지기 시작하면 상태로 승격한다」**였다. 공중은 그 기준을 넘는다 —
이동 제어가 다르고(공중 제어력), 구르기가 안 되고, 착지 판정이 필요하고, 공격이 다르다.
이 넷을 `if (!grounded)` 로 흩뿌리면 상태 머신을 만든 이유가 사라진다.
원칙 위반이 아니라 **원칙의 적용**이다.

> 다양성은 여전히 데이터에서 나온다 — 공격이 5종이어도 `Attack` 은 하나다(§3.2.1).

### 3.8.2 점프 중 공격 **확정**

무브셋에 `jump` 가 하나 늘어난다(§3.2.1).

★ 공중에서 내려찍으면 **머리에 닿기 쉽다** — 적보다 위에 있기 때문이다.
머리는 즉사(§3.2)이므로 「높은 곳에서 뛰어내려 머리를 노린다」가 성립한다.
지형(발판)이 전술의 일부가 되는 순간이고, 이것이 플랫포머로 옮기는 진짜 이득이다.

### 3.8.3 웅크리기 키는 `Ctrl` 유지 **확정**

↓ 방향키가 플랫포머의 관례지만 `Ctrl` 을 유지한다.
↓ 는 나중에 **아래 발판으로 내려가기**(내려찍기 / 통과 가능한 발판)에 쓸 여지가 있고,
조작을 한 번 익힌 뒤 바꾸는 비용이 크다.

### 3.8.4 구현 결과 (6-c-8, 2026-09-14) **확정**

「미결정」 세 칸이 숫자와 결정이 되었다.

| 항목 | 값 | 왜 |
|---|---|---|
| 공중 제어력 | **0.6** | 0 은 「뛰면 끝」이라 답답하고, 1 은 무게가 사라진다. 숫자 하나라 조정이 싸다 |
| 이단 점프 · 벽 타기 | **없음** | 지형 설계가 통째로 달라진다. 나중에 **추가는 쉽고 빼는 것은 어렵다** |
| 낙하 데미지 | **없음** (보류) | 발판(6-d)이 와야 의미가 생긴다. 그때 **다리 부위 파괴**와 엮으면 좋은 소재다 |

그 밖에 이번에 정해진 것:

| 항목 | 결정 |
|---|---|
| 점프 키 | **Space / 패드 A.** 공격이 이미 좌클릭이 주 입력이라 자리를 비울 수 있었다 |
| 무기를 **버리는** 키 | **없다.** 무기가 땅에 떨어지는 경우는 **팔이 잘렸을 때**(§3.2.2)뿐이다 — 「버린다」는 8단계 인벤토리의 몫이고, 그 전에 키를 주면 되돌릴 방법 없이 맵에 무기가 흩어진다. ※ 확인용으로 `F7`(오른팔 파괴)을 둔다 |
| 줍기 키 | **`E`**(상호작용). ★ 두 번 옮겼다: 공격 키로 갔다가(Space 로 두면 **뛰어넘기만 해도 주워진다**) 다시 E 로 왔다 — 무기를 밟고 선 동안 손이 막혔다. **E 도 땅 위에서만** 들으므로 「뛰어넘으며 주워진다」는 막힌 채다 |
| 공중에서 피격 | 경직 + 수평 넉백 + 그대로 낙하. 「공중은 무방비」가 §3.1 과 맞는다 |
| 공중에서 구르기 · **상호작용(E)** | 불가. 「점프 + 구르기」가 되면 무적으로 날아다니게 된다. E 는 줍기·포탈·화톳불에 **같은 조건**을 건다 |
| 웅크린 채 점프 | 불가. 웅크리기는 상태가 아니라 **수식자**라 조합을 늘리면 경우의 수가 폭발한다 |

**숫자** (`BodyComponent` / `PlayerController`):

| | 값 | 결과 |
|---|---|---|
| 중력 | 0.35 px/틱² | |
| 점프 초속 | 6.2 px/틱 | 정점 ≈ **55픽셀** / 정점까지 18틱 / 체공 ≈ 35틱 |
| 최대 낙하 속도 | 9.0 px/틱 | 없으면 긴 낙하에서 바닥을 **뚫는다** |
| 지면 높이 | y = 280 | 캐릭터 키 62 → 머리 218. 하단 UI(294~)와 겹치지 않는다 |

★ **55픽셀은 우연이 아니다.** 적의 머리 상자가 「발끝에서 37~55 위」다.
즉 점프 궤적의 중간쯤이 정확히 머리 높이를 지나간다 —
§3.8.2 의 「높은 데서 뛰어내려 머리를 노린다」가 **숫자로** 성립한다.

## 3.8.5 적이 여럿일 때 **확정** (2026-09-15)

| 항목 | 결정 | 왜 |
|---|---|---|
| 한 번 휘두르면 | **한 명** | 전원 타격이면 광역기가 공짜가 되고, 무리를 한 번에 정리할 수 있어 **시야(§3.9 B)도 지형(§4.0.1)도 다시 무의미해진다** |
| 적이 동시에 때리는 것 | **막지 않는다** | 몰려 있는 대가다. 대신 구르기 한 번이 **동시에 들어온 둘을 다** 흘린다 — 무적은 공격마다가 아니라 **틱마다**이기 때문이다 |
| 적끼리 겹침 | **뒤에 선 적이 한 칸 물러서서 기다린다** | 몸끼리 충돌은 별도 시스템이고 AI 도 커진다. **멈추는 거리만** 늘리고 공격 사거리는 안 건드린다 — 둘을 같이 늘리면 뒤의 적이 **닿지도 않는 거리에서 휘두른다** |

★ 「누가 더 가까운가」는 **Scene 이 판단해 알려 준다.** 적이 서로를 알 필요가
없다 — 두 몸 사이의 판정을 Scene 이 하는 것과 같은 이유다(§9).

★★ 스폰 목록(`EnemySpawn`)은 **앞으로의 맵 파일 그 자체**다. 지금은 코드에
적혀 있지만 `Level` 의 사각형 목록과 함께 `map.json` 으로 나간다.
그래서 지금부터 **데이터 모양**으로 두었다 — 「좌표 목록을 훑어 만든다」가
파일에서 읽어 와도 그대로 성립한다.

## 3.9 시야 (FOV) — **A · B 둘 다 확정** (2026-09-10)

> 「현실처럼 보이는 범위를 제한한다」. **둘은 같은 규칙의 양면이다.**

### A. 플레이어의 시야 — 어둠

화면 전체가 어둡고, 플레이어 주변과 **바라보는 방향**만 보인다.

★ **이미 기획서의 뼈대다.**
§1.1 의 `蛍の指輪`(「어둠 속이 보이게 된다」)와 §4 의 `暗黒の洞窟` 이 이것을 전제로 적혀 있다.
그리고 §1.2 의 지문 슬롯 2개의 기회비용도 여기서 성립한다 —
「蛍을 빼면 횃불을 들어야 하고, 횃불은 한 손을 차지해 양손 무기를 못 쓴다」.

**즉 이 시스템이 없으면 蛍の指輪 은 존재할 수 없다.**

구현: 캔버스에 다 그린 뒤 마스크를 곱한다.
★ **2패스 구조가 이미 있어서 3패스로 늘리면 된다.** §3.7 이
「포스트 프로세싱(비네팅·색보정·블룸)의 토대가 그대로 생긴다」고 적어 둔 바로 그 자리다.

### B. 적의 시야 — 인지

적이 플레이어를 감지하는 범위를 **원형 거리에서 방향 있는 부채꼴로** 바꾼다.
지금은 `kEnemySightRange` 가 단순 거리라서 **등 뒤에 있어도 본다.**

뒤에서 다가가면 안 보인다 → 기습이 성립하고, 「어느 쪽에서 접근할까」가 판단이 된다.

구현: 싸다. 거리 판정에 각도 하나를 더하는 정도다.

### ★ 둘은 같은 규칙의 양면이다

§3.2 에 이렇게 적혀 있었다 —

> **머리 파괴의 대칭성**: 蛍の指輪을 빼면 *내가* 어둠 속에 있고,
> 머리를 부수면 *적이* 어둠 속에 있다. 같은 규칙이 양쪽에 적용된다.

머리 = 즉사로 정하면서(§3.2) 이 대칭을 폐기했는데, **FOV 를 넣으면 되살아난다.**
A 는 내 시야, B 는 적의 시야이고, 「보이지 않으면 싸울 수 없다」가 양쪽에 걸린다.

### B 구현 결과 (6-f-1, 2026-09-14) **확정**

| | 값 | 왜 |
|---|---|---|
| 부채꼴 | **±55°** · 사거리 220 | 좁으면 정면에서도 안 보여 어색하고, 넓으면 뒤로 도는 의미가 없다 |
| **청각** | 반경 **40** (각도 무관) | 없으면 **뒤에 붙어 무한히 때릴 수 있다.** 플레이어의 공격 사거리(12~40)와 겹치는 것이 요점 — 「붙기 전까지는 안전하지만 **때리려면 들킨다**」 |
| **잊어버리기** | **120틱(2초)** | 없으면 기습이 **첫 1회만** 의미 있다. 한 번 들키면 영원히 쫓기므로 발판으로 도망치는 것도 소용없어진다 |
| 기습 보너스 | **없음** | 부위 파괴가 이미 그 역할을 한다. 규칙을 겹치면 둘 다 흐려진다 |

★ **세로 차이가 크면 자동으로 안 보인다.** 각도를 `cos` 으로 재므로
위쪽은 부채꼴 밖으로 빠진다 — **발판 위로 올라가면 숨을 수 있다**가
규칙 한 줄에서 따라 나온다. 6-d 의 「지형이 방패가 된다」와 같은 자리다.

★ `cos` 끼리 비교한다. 각도를 구하려면 `atan2` 가 필요하지만 **비교만 할
거라면 cos 비교로 충분하다** — 삼각함수 호출이 사라진다.

### A 구현 결과 (6-f-2, 2026-09-14) **확정**

★★ **렌더 패스를 늘리지 않았다.** 기획서는 「캔버스에 다 그린 뒤 마스크를
곱한다 = 3패스」로 적어 두었는데, 실제로는 **가운데가 투명하고 바깥이 검은
그림을 한 장 덮으면** 끝이었다. 알파 블렌딩이 그대로 「보이는 만큼만 보인다」가
된다. 셰이더도 새 렌더 타깃도 필요 없다.

> **「어떻게 만들까」보다 「무엇이면 충분한가」를 먼저 묻는 편이 싸다.**

| 항목 | 결정 |
|---|---|
| 모양 | **원형 + 앞쪽이 더 멀리**(뒤 130 / 앞 300 / 위아래 150). 그림 한 장을 `facing` 으로 반전 |
| 진하기 | **알파 0.88.** 완전한 검정이 아니다 — 완전히 가리면 지형을 못 읽고, **적의 `!` 예고가 안 보여 불공평**해진다 |
| 켜고 끄기 | 지금은 상수 + **F5**. 7단계에서 **장소의 성질**이 된다 |

★ 진하기를 그림에 **굽지 않는다.** 가장자리를 알파 255 로 만들고 실제 진하기는
그릴 때 틴트로 정한다 — 장소마다 다르게 두어도 그림을 다시 안 만든다.

★ 그리는 순서가 규칙이다: **그림 → 어둠 → 판정 상자(F1) → HUD.**
어둠을 디버그 위에 덮으면 어두워서 상자를 못 본다.

### 3.9.1 손 슬롯 UI **확정** (2026-09-14)

★ 글자가 아니라 그림인 이유는 §3.2.3 과 같다 — 몸 상태를 이미 그림으로

## 3.10 인벤토리 · 장비 **확정** (2026-09-10 계획 추가)

> 아이템을 가지고 다니고, 무기와 방어구를 갈아입는다.

### ★ 절반은 이미 만들어져 있다

새 시스템이 아니라 **흩어져 있는 것을 묶는 작업**이다.

| 이미 있는 것 | 어디서 |
|---|---|
| `ArmorData { name, poise }` + F2 로 교체 | §3.1.1 강인도. **장비 교체가 이미 동작한다** |
| 무기 = 공격 여러 개(무브셋) | §3.2.1. 「무기를 바꾼다 = 무브셋을 바꾼다」 |
| 지문 슬롯 2개 | §1.2 확정 |
| 죽어도 장비가 남는다 | §3.6.1 `Respawn()` 의 「남는다」 칸에 이미 `m_armorIndex` 가 있다 |

**인벤토리는 그 「남는다」 칸이 커지는 것이다.**

### 원칙 — 장비는 강해지는 것이 아니라 **무엇을 포기하는가**

§1.2 가 지문에 대해 정한 규칙을 장비 전체로 넓힌다.

| 장비 | 얻는 것 | 잃는 것 | 상태 |
|---|---|---|---|
| 무거운 방어구 | 경직 없음(poise) | 구르기가 느리다. **HP 로 지불한다** | ✅ 구현됨 |
| 무거운 무기 | 한 방이 크다 | 느리다. **아이는 못 든다**(§3.3) | 데이터만 |
| 양손 무기 | 강하다 | 횃불·방패를 못 든다 → **어둠 속에서 싸운다**(§3.9 A) | 계획 |
| 지문 2슬롯 | 인식이 바뀐다 | 다른 지문을 뺀다 | §1.2 확정 |

★ **네 줄이 전부 같은 문장이다.** 「강해지는 대신 무엇을 포기하는가」.
새 장비를 추가할 때 이 표에 한 줄로 적히지 않으면 그 장비는 기획에 안 맞는 것이다.

### ★ 손 슬롯은 8단계를 기다리지 않고 먼저 왔다 (2026-09-10)

절단이 그것을 앞으로 당겼다 — 「팔이 잘리면 그 손의 무기를 떨군다」는 규칙이
**어느 손에 들고 있는가**를 필연적으로 요구하기 때문이다.

```
오른손  무기   ← 잘리면 떨군다
왼손    보조   ← 횃불 / 방패 / 없음
```

★ 오른팔을 잃고 무기를 주우면 **왼손**에 든다. 그런데 왼손은 보조 슬롯이므로,
그때부터 횃불을 들 수 없다 — §3.9 A(어둠)가 오면
**「무기를 되찾은 대가로 어둠 속에서 싸운다」**가 된다.
§1.2 의 기회비용이 슬롯 구조만으로 또 성립한다. 새 규칙이 필요 없다.

### 슬롯 구성 (안)

```
무기      1   무브셋을 통째로 바꾼다
보조 손   1   횃불 / 방패 / 없음(= 양손 무기)
방어구    1   강인도 · 무게
지문      2   §1.2 확정
```

★ 보조 손이 §1.2 의 기회비용을 실제로 만든다 —
「蛍の指輪을 빼면 횃불을 들어야 하고, 횃불은 한 손을 차지해 양손 무기를 못 쓴다」가
**슬롯 구조 하나로 성립한다.** 규칙을 따로 쓸 필요가 없다.

### 인벤토리 화면은 Scene 이다

`PauseScene` / `DeathScene` 과 같은 구조를 그대로 쓴다
(`DrawsBelow = true` / `UpdatesBelow = false` — 뒤에 게임이 멈춘 채 보인다).
Scene 스택을 만들어 둔 것이 세 번째로 값을 하는 자리다.

### 필요한 것

| | |
|---|---|
| `items.json` | 6-g(JSON) 뒤. `weapons.json` / `armors.json` 과 같은 스키마 |
| 획득 경로 | 적 드롭 / 상자 / 기도 포인트(§3.5) |
| 폰트 | 아이템 이름·설명문은 한국어·일본어다 → **런타임 글리프 아틀라스**(§6.5)가 먼저 |

### 미결정

| 항목 | 메모 |
|---|---|
| 방어구를 부위별로 나눌까 | 적은 부위 파괴가 있지만 플레이어는 단일 HP 다(§3.2 는 적 전용). 방어구도 하나가 자연스럽다 |
| 무게(하중) 시스템 | 다크소울식 총 무게 → 구르기 속도. §3.3 의 「아이는 무거운 무기를 못 든다」와 같은 축이다 |
| 소지품 개수 제한 | 있으면 「무엇을 버릴까」가 생기고, 없으면 관리가 편하다 |
| 아이템 설명문 | §5 가 「아이템 설명문」을 서사 전달 수단으로 이미 꼽아 두었다 |

## 3.11 방패 · 방어 **계획 확정** (2026-09-16)

> **방패를 들고 있으면 막는다. 막히는 높이는 방패 크기가 정하고,
> 하단은 앉아서 막는다.**

### ★ 새로 만들 것이 거의 없다

이 게임이 이미 가진 것들 위에 그대로 얹힌다.

| 이미 있는 것 | 방패가 그것을 어떻게 쓰는가 |
|---|---|
| 공격이 **띠**다 (§3.2.1) | 방패도 **상자**다. 겹치면 막힌다 — 같은 AABB 판정 |
| **버튼 = 손** (§3.2.1.1) | 왼손에 방패를 들면 **좌클릭이 곧 방어**가 된다. ★ 조작을 새로 만들 필요가 없다 |
| **자세**가 상자를 옮긴다 (§3.8) | 앉으면 방패 상자도 같이 내려간다 — 「앉아서 하단을 막는다」가 **규칙 없이 따라 나온다** |
| 왼손 = 보조 슬롯 (§3.10) | 방패를 들면 **횃불을 못 든다** → 어둠(§3.9 A) 속에서 싸운다. §1.2 의 기회비용이 그대로 성립 |
| 스태미나 (§3.1) | 막는 데 드는 값 |
| 강인도 · impact (§3.3) | 가드 브레이크의 기준이 이미 있다 |
| `weapons.json` (§3.2.1.2) | `shields.json` 이 같은 패턴으로 붙는다 |

★★ 특히 **「앉으면 하단을 막는다」에 특수 규칙이 필요 없다**는 점이 중요하다.
방패 상자를 몸에 붙여 두면 자세가 바뀔 때 같이 내려가고, 그러면
**높은 곳이 비고 낮은 곳이 덮인다** — 이 프로젝트가 계속 써 온 방식
(좌표로 성립하게 만들고 규칙을 안 쓴다) 그대로다.

### 성립하는 구조

```
        37~55  상단        큰 방패는 여기까지 덮는다
        26~36  중단        작은 방패도 덮는다
         2~20  하단        서 있으면 못 막는다 -> **앉는다**

    앉으면 방패가 내려간다 = 하단을 덮고 상단이 빈다
```

★ 방패 크기가 **덮는 띠의 높이**다. 큰 방패는 상단까지 덮지만
무겁고(이동·스태미나), 작은 방패는 중단만 덮는 대신 가볍다 —
숫자 하나가 곧 성격이 된다. 무기의 `heightFromFoot` 와 같은 구조다.

### 미결정

| 항목 | 메모 |
|---|---|
| 막으면 데미지 | 0 / 감소 / 스태미나로 대신 낸다 |
| 가드 브레이크 | `impact` 가 방패의 강인도를 넘으면 뚫린다? |
| 패링 | 막기 시작한 **첫 몇 틱**만 특별 판정. 구르기 무적과 같은 구조로 붙는다 |
| 방향 | 등 뒤에서 오는 것은 못 막는다(§3.2.2 의 「몸을 돌려 막는다」와 이어진다) |
| 적도 드는가 | 방패 든 적 = 「위나 아래로 돌려야 하는 적」 |

## 3.12 무기 튕김 **계획 확정** (2026-09-16)

> **벽이나 단단한 방패를 치면 공격이 튕긴다.**
> 휘두르기가 거기서 끊기고, 친 쪽이 짧게 경직되며 뒤로 밀린다.

### ★ 이것도 새로 만들 것이 적다

| 이미 있는 것 | 튕김이 그것을 어떻게 쓰는가 |
|---|---|
| `Level::ForEachOverlapping` | 「이 공격 상자가 **벽과** 겹치는가」를 그대로 물을 수 있다 |
| `PoiseComponent` (§3.3) | 튕긴 쪽의 경직. 이미 있는 구조 |
| `DecayingStep` (넉백) | 뒤로 밀리는 것. 이미 있는 공식 |
| `m_hitThisSwing` | 「이 휘두르기는 끝났다」를 표시하는 자리가 이미 있다 |
| `impact` (§3.3) | 방패의 단단함과 비교할 값이 이미 있다 |

### ★★ 이것이 지형에 **세 번째 역할**을 준다

지금 벽은 **막는 것**(6-d)과 **숨는 곳**(6-f, 발판 위는 시야 밖)이다.
여기에 「**휘두를 자리가 있는가**」가 붙는다 —

- 좁은 통로에서 **큰 무기를 휘두르면 튕긴다** → 무기 크기와 지형이 맞물린다
- 벽을 등지고 싸우면 위험해진다
- `reach` · `width` 가 데미지만이 아니라 **쓸 수 있는 장소**를 정하게 된다

★ 무기의 숫자가 이미 「닿는 부위」를 정하고 있었는데(§3.2.1),
여기에 「**설 수 있는 자리**」까지 정하게 된다. 숫자 하나가 또 한 겹 일한다.

### 방패와 한 쌍이다 (§3.11)

| 방패의 단단함 vs 공격의 `impact` | 결과 |
|---|---|
| 방패가 더 단단하다 | **공격이 튕긴다** (치는 쪽이 경직) |
| `impact` 가 더 크다 | **가드 브레이크** (막는 쪽이 경직) |

★ 같은 두 숫자의 비교가 **양쪽 결과를 다 만든다.** 규칙을 하나 더 만들지 않는다.
강인도(§3.3)가 「버틴다 / 휘청인다」를 정하는 것과 완전히 같은 모양이다.

### 미결정

| 항목 | 메모 |
|---|---|
| 무엇에 튕기는가 | 벽 전부? 아니면 「단단한」 지형만 (나무 상자는 부서진다) |
| 언제 판정하는가 | `active` 시작 시 한 번? 매 틱? — 매 틱이면 휘두르는 도중에 벽에 들어가도 튕긴다 |
| 스태미나 | 튕기면 더 잃는가 |
| 소리·화면 | 「금속음 + 화면 흔들림」이 튕김의 전부일 수도 있다 |

## 4. 맵 구조 — 넓은 맵 + 카메라 추적 **확정** (2026-09-10 변경)

### 4.0 지형 데이터 — 지금은 사각형, 나중에 타일맵 **확정** (2026-09-14)

2D 플랫포머의 표준은 **타일맵**이다. 편집기(Tiled / LDtk)로 그리고 **JSON** 으로
내보낸다. 타일맵이 이기는 이유는 편집이 아니라 **질의 비용**이다:

| | 사각형 목록 | 타일맵 |
|---|---|---|
| 충돌 질의 | 전부 훑는다 `O(n)` | 좌표 → 배열 인덱스 `O(1)` |
| 넓은 맵 | 가속 구조를 직접 짜야 한다 | 그냥 배열 |

그런데 지금은 화면 한 장에 발판 넷이다. 여기서 타일맵을 만드는 것은
**「무브셋 → JSON」** 과 같은 실수다 — 구조가 확정되기 전에 그릇을 만들면 두 번 짠다.

★ 그래서 **지금 고정하는 것은 저장 형식이 아니라 「질문의 모양」이다.**

```
Level 에게 묻는다:  이 상자와 겹치는 고체를 훑어 달라   (ForEachOverlapping)
                   이 x 의 발밑에 바닥이 있는가         (HasFloorBelow)
```

이 둘은 타일맵이 되어도 **그대로 있는 개념**이다. 속이 배열에서 격자로 바뀔 뿐
부르는 쪽은 한 줄도 안 바뀐다. 교체 시점은 맵이 실제로 넓어지는 6-e 다.

### 4.0.4 맵 파일과 포탈 **확정** (2026-09-16)

`assets/data/maps/*.json` 한 장이 맵 하나다.

```
{ world: {w, h, groundY}, entries: {...}, solids: [...], enemies: [...],
  portals: [...], savePoints: [...] }
```

★ **새로 만든 것이 거의 없다.** 지형은 이미 「사각형 목록」이었고(6-d),
적 배치도 이미 「좌표 목록」이었다(7-a). 둘 다 **데이터 모양으로 만들어 둔 덕에**
파일로 옮기는 것이 형태를 안 바꿨다 — 코드의 배열이 파일의 배열이 됐을 뿐이다.

★★ **포탈은 좌표가 아니라 「입구 이름」을 가리킨다.**

```json
{ "box": [1872, 624, 1908, 680], "to": "cave", "entry": "west" }
```

좌표로 적으면 저쪽 맵을 고칠 때마다 이쪽도 고쳐야 한다 — **같은 값이 두 곳에**
있는 것이고, 이 프로젝트가 계속 밟아 온 함정이다.

★ 맵을 바꿀 때 **Scene 을 새로 만들지 않는다.** `PlayScene` 이 내용만 갈아
끼운다 — Scene 을 바꾸면 플레이어의 HP·부위·무기를 옮겨야 하고, 그건
§3.6.1(「남는다 / 되돌아간다」)과 얽혀 복잡해진다. **맵을 건너는 것은
되돌아가는 것이 아니다** — 몸 상태는 전부 그대로 간다.

★ 넘어가는 것은 **틱의 맨 끝**이다. 판정 도중에 적 목록과 지형을 갈아 끼우면
순회 중인 것이 사라진다 — `SceneManager` 가 전환을 미루는 것과 같은 이유다.

★★ **지면(groundY)도 맵이 정한다.** 전역 상수 하나였을 때는 맞았지만,
동굴(600)에서 들판의 지면(680)에 놓이면 바닥 속이다 —
「하나뿐이라 괜찮았던 것」이 또 터진 자리다.

### 4.0.5 상호작용(E)과 세이브 포인트 **확정** (2026-09-16)

**포탈은 들어가는 것만으로 안 넘어간다. 안에서 `E` 를 눌러야 넘어간다.**

밟자마자 넘어가면 **되돌아올 때도 밟자마자 넘어간다** — 문 앞에서 두 맵을
왕복하는 사고가 난다. 그리고 「들어갔다」는 플레이어가 **결정한 적이 없다.**
공격 버튼과 같은 기준이다: 세계를 바꾸는 일은 눌러서 한다.

★★ **버튼은 하나다.** 무엇이 일어나는지는 **그 자리에 무엇이 있는지**가 정한다.

| 그 자리에 있는 것 | `E` 가 하는 일 | 화면에 뜨는 글자 |
|---|---|---|
| **땅에 떨어진 무기** | 줍는다 | `E : PICK UP` |
| 포탈 | 다른 맵으로 | `E : ENTER` |
| 세이브 포인트 | 쉰다 | `E : REST` |
| (나중) 상자 | 연다 | `E : OPEN` |
| (나중) 사람 | 말을 건다 | `E : TALK` |

★ 겹치면 **무기가 먼저**다. 화톳불은 도망 안 가지만 쉬면 적이 되살아난다 —
**되돌릴 수 없는 쪽을 뒤로** 민다.

★★ **줍기가 손 버튼에서 E 로 옮겨 왔다** (2026-09-16). 전에는 「발밑에 무기가
있으면 그 버튼이 줍기」였는데, 그러면 **떨군 무기를 밟고 선 동안 휘두를 수가
없다** — 손이 통째로 막힌다. E 로 옮기자 좌/우클릭은 **언제나 손**이 되어
§3.2.1.1 이 오히려 깨끗해졌다.

대신 **어느 손에 들지를 못 고르게** 됐다. 규칙은 **주손(오른손) 우선, 그 팔이
부서졌으면 반대 손**이다. §1.2 의 기회비용(왼손을 무기로 채우면 횃불을 못 든다)은
**8단계 장비 화면**으로 옮긴다 — 줍는 순간에 고르게 하면 「집어 든다」와
「장착한다」가 한 동작에 붙어 **되돌릴 수가 없다.**

좌/우클릭이 **손**을 가리키고 그 손에 든 것이 공격을 정하는 것과 같은 구조다
(§3.2.1.1). 그래서 종류가 늘어도 **버튼도, 찾는 코드도 안 늘어난다** —
`MapInteract` 한 목록에 `kind` 만 붙는다.

★ 누르기 **전에** 찾아 둔다(`m_focus`). 안 그러면 「지금 E 를 누를 수 있다」를
화면에 못 보여 주고, 플레이어는 그 위에 서 있어도 모른다.

---

**세이브 포인트에서 쉬면 세 가지가 한꺼번에** 일어난다 — 소울류의 화톳불이다.

1. **몸이 회복된다** (부위 HP·스태미나·포이즈)
2. **적이 전부 되살아난다**
3. **부활 지점이 여기가 된다** (맵 이름까지 같이 기억한다)

★★ 셋이 **한 묶음**이어야 「쉬어 갈까」가 **판단**이 된다. 회복만 주면 공짜라
무조건 쉬고, 부활 지점만 옮기면 회복하러 갈 이유가 없다. 세 개를 묶는 순간
「지금 쉬면 뒤에 정리해 둔 적이 다시 선다」는 값을 치르게 된다.

★ 쉬는 것과 죽는 것이 **되돌리는 범위가 같다** — §3.6.1 의 「되돌아간다」 칸
그대로다. 무기를 어디에 떨궜는지, 어떤 방어구를 입었는지는 **둘 다 안 건드린다.**

★ 부활은 이제 **맵의 시작이 아니다.** 맵이 다르면 그 맵을 다시 읽는다 —
동굴에서 죽어도 들판에서 쉬었으면 들판에서 일어난다.
맵을 지나간 것만으로 부활 지점이 바뀌면 **되돌아갈 이유가 사라진다.**

★★ 부활 지점은 **x 와 y 를 같이** 기억한다. 세로를 「맵의 지면」으로 두었을 때는
맞았다 — 부활 지점이 맵 시작 하나뿐이고 그건 언제나 지면 위였으니까.
발판 위에 화톳불을 하나 놓는 순간, 거기서 쉬고 죽으면 **아래 지면에서** 일어났다.
또 「하나뿐이라 괜찮았던 것이 둘이 되는 순간 터진다」다.

높이의 출처는 **화톳불 상자의 아랫변**이다. 화톳불이 놓인 바닥이 곧 그 값이라
따로 적을 것이 없다 — 발판 위에 두면 상자도 같이 올라가 있다.

### 4.0.2 카메라 — **데드존** 추적 **확정** (2026-09-14)

월드는 **1920 x 760**(가로 3화면 · 세로 2화면), 카메라가 두 축으로 따라간다.

| 방식 | |
|---|---|
| 즉시 추적 | 한 걸음마다 화면 전체가 따라 흔들려 멀미가 난다 |
| **데드존** | 화면 가운데 사각형(±56 x ±36)을 벗어날 때만 민다 |
| 보간(lerp) | 부드럽지만 **「그리기는 정수」와 싸운다** — 틱당 0.3픽셀이 반올림되어 튄다 |

★ 따라가는 지점은 발밑이 아니라 **가슴 높이**(발끝 +24)다.
발밑을 따라가면 점프할 때마다 화면이 아래로 쏠린다 — 눈이 쫓는 것은 몸이다.

★ 월드 바닥까지 80픽셀을 남겼다. 카메라가 맨 아래에 붙었을 때 지면이
화면 y=280 에 오게 하려는 것이다 — **세로 스크롤이 생겨도 서 있는 그림은
예전과 같은 자리**에 온다. 화면 아래 ~66픽셀은 몸 UI 가 쓴다.

★ 시차 배경 **2겹**(깊이 0.22 / 0.55). 깊이가 다른 것이 둘만 있어도 눈은
거리를 읽는다. 먼 층은 **옅게**(공기에 묻힌다), 가까운 층은 **짙게**(실루엣) —
배경 지우기 색을 기준으로 **양쪽으로 벌려야** 층이 갈린다.
배경은 **지형이 아니다** — `Level` 에 넣으면 밟히고 막힌다.

### 4.0.3 발판 배치의 세 조건 **확정** (2026-09-14)

| | 값 |
|---|---|
| ① 세로 간격 < 점프 정점 | 56 < 66 |
| ★ ② 세로 **틈**(간격 - 두께) > **몸 높이** | 48 > 44 |
| ③ 가로 간격 < 공중 이동 거리 | 32 |

★★ ②가 핵심이다. 「올라갈 수 있는가」는 점프 높이만의 문제가 아니라
**올라가서 설 자리가 있는가**까지가 조건이다. 틈이 몸보다 좁으면 그 자리는
강제 웅크리기가 되고, 웅크리면 점프가 막히므로 위로 갈 방법이 사라진다.

※ 점프 정점은 `v0²/2g`(=70)이 아니라 **틱마다 더한 값 66** 이다.
고정 타임스텝에서는 연속시간 공식이 참고값일 뿐이다.

### 4.0.1 발판은 **통과할 수 없다** **확정** (2026-09-14)

「위에서 내려올 때만 밟히는」 통과형은 옆면 충돌이 필요 없어 싸지만,
↓ 로 내려가기와 한 묶음이다. **↓ 는 나중에 사다리에 쓰기로** 했으므로
발판은 그냥 벽으로 둔다.

★ 화면 좌우 끝도 **지형**이다. 전에는 이동 코드마다 `clamp` 를 걸었는데,
벽으로 두면 걷기·구르기·넉백이 전부 같은 규칙으로 막힌다 —
**예외를 없애려면 그것도 규칙 안에 넣는다.**

화면보다 **넓은 맵**을 만들고, 카메라가 플레이어를 따라 움직인다.
측면 뷰 플랫포머(§3.8)이므로 좌우로 길고 위아래로도 층이 있는 맵이 된다.

### 예전 결정(고정화면 방 그래프)을 뒤집었다

원안은 「화면은 항상 한 장, 문으로 나가면 다음 방」(젤다 1편 / Binding of Isaac 식)이었고,
그 근거는 **비용**이었다. 뒤집었으므로 그 이점들이 전부 사라진다. 정직하게 적어 둔다.

| 잃는 것 | 대신 필요한 것 |
|---|---|
| 「카메라 시스템이 필요 없다」 | 카메라 추적 · 맵 경계 clamp · 데드존 |
| 「타일맵 스트리밍 불필요」 | 화면 밖 지형·적을 어떻게 다룰지(컬링) |
| 「세이브가 단순 — 어느 방에 있었나 하나」 | 맵 + 좌표. §3.5 기도 포인트가 그 역할을 한다 |
| 「방 하나씩 = 작업 단위가 명확」 | 맵 하나가 커져서 한 덩어리의 작업량이 늘어난다 |

**Why(그럼에도 뒤집는 이유):** 고정화면은 「한 화면 안에서 벌어지는 일」로 게임을 가두고,
넓은 맵은 **탐험**을 가능하게 한다. 소울라이크의 「길이 이어져 있다는 감각」과
§1.1 의 지문 시스템(어둠 · 환영 · 숨은 것)은 넓은 공간에서 훨씬 강하게 작동한다.

### 다행히 절반은 이미 만들어져 있다

`Camera` 클래스가 이미 있다 — 위치 · 줌 · 화면 흔들림 · 뷰 행렬.
화면 흔들림 때문에 만들었던 것이 그대로 추적 카메라의 토대가 된다.
그리고 **2패스 저해상도 캔버스(640×360)는 그대로 유효하다** — 카메라가 움직여도
내부 해상도는 바뀌지 않는다(§3.7).

```
    [집]───[마을 길]───[광장]
                          │
                     [기도의 장소]
                          │
                   [동굴 입구]───[暗黒の洞窟]───[보스]
```

맵**들**을 잇는 구조 자체는 남는다. 달라지는 것은 **한 칸의 크기**다 —
「화면 한 장」이 아니라 「화면 여러 장 넓이의 구역」이 된다.

## 6.5 대화 시스템 (엔진 기능으로 예정) — 미착수

「컷신을 쓰지 않는다」(5장) 결정 때문에 **텍스트가 서사 전달의 거의 전부**다.
그래서 대화는 게임 코드가 아니라 **엔진이 제공하는 기능**이어야 한다.

### 표시 방식 두 가지

| 방식 | 쓰이는 곳 |
|---|---|
| **말풍선** — 캐릭터 옆에 붙어 따라다닌다 | 짧은 대사, 적의 임종 대사, 기도의 말 |
| **전체 화면** — 하단 또는 전면 상자 | 긴 대화, 아이템 설명, 亡者の指輪의 환영 |

★ 둘은 **표시 방법만 다르고 진행 로직은 같다.**
「대사 목록을 순서대로 넘긴다」는 부분(DialogueRunner)을 공유하고,
말풍선/전체화면은 그것을 그리는 뷰(View)로만 나눈다. 로직을 두 벌 만들지 않는다.

### 데이터 형식 — 미결정

대사를 코드에 박으면 안 된다. 외부 파일로 뺀다.

| 후보 | 장단 |
|---|---|
| JSON | 6단계에서 어차피 도입. 구조가 명확하지만 긴 문장을 쓰기엔 답답 |
| CSV / TSV | 표 형태라 번역·검수에 강함. 분기 표현이 약함 |
| 전용 스크립트 (Ren'Py / Yarn Spinner 식) | 사람이 쓰기 가장 편하고 분기·조건에 강함. 파서를 직접 만들어야 함 |

**대사 ID → 텍스트 테이블** 구조를 권한다. 코드는 ID 만 알고,
언어 전환이 테이블 교체로 끝난다(한국어/일본어/영어).

### 알려진 장애물

- **폰트**: 현재 BitmapFont 는 ASCII 전용. 한국어·일본어는 글자 수가 많아
  전부 미리 굽는 방식이 통하지 않는다. **런타임 글리프 아틀라스**가 따로 필요하다.
  (필요한 글자가 나올 때마다 아틀라스에 채워 넣는 방식)
- **타자기 효과**: 한 글자씩 나타나는 연출. 틱 단위로 세면 되므로
  고정 타임스텝 덕에 쉽다. 「n 틱마다 한 글자」.
- **줄바꿈**: 상자 폭에 맞춰 단어 단위로 접기. 한국어·일본어는 단어 경계가
  공백이 아니라서 규칙이 다르다.

## 8. 기술적 영향

기획 확정에 따라 원래 로드맵에 생기는 변화.

### 8.1 부위 파괴 → 적은 단일 스프라이트가 될 수 없다

가장 큰 영향. 적이 「팔이 잘린 상태」를 표시해야 하므로 **스프라이트 구조가 달라진다.**

| 방식 | 장점 | 단점 |
|---|---|---|
| 부위별 스프라이트를 겹쳐 그림 | 조합 폭발 없음 | 관절이 뻣뻣해 보이기 쉬움 |
| 상태별 애니메이션 세트를 따로 그림 | 보기 좋음 | 그림 양이 상태 수만큼 배증 |
| **하이브리드(권장)** | 다리 파괴만 전용 애니메이션(기기), 팔·머리는 겹쳐 그리기로 제거 | |

**로드맵 2단계(SpriteBatch)와 4단계(스프라이트시트 애니메이션)에 영향.**
나중에 고치면 비싸므로, 4단계 설계 시 「적 = 파츠의 집합」을 전제로 만든다.

#### 실제로 어떻게 되었나 (6-c-7, 2026-09-14) **확정**

하이브리드 그대로 갔다. 다만 **예상과 한 가지가 달랐다.**

> 「팔을 겹쳐 그리기로 **제거**한다」고 적었는데, 몸 시트에는 **팔이 애초에 없었다.**
> 통짜 사각형 몸통이라 제거할 팔이 없다. 그래서 **먼저 더해야** 했다.

그래서 시트가 네 장이다. 팔과 상처가 정확히 반대로 켜진다.

| 레이어 | 언제 보이는가 |
|---|---|
| `player_arm_front` / `player_arm_back` | 그 팔이 살아 있을 때 |
| `player_stump_front` / `player_stump_back` | 그 팔이 잘렸을 때 |

**★ 머리 레이어는 만들지 않았다.** 머리 파괴 = 즉사(§3.2.2)라
「머리 없는 몸」을 화면에 보여줄 일이 없다. 규칙 하나가 에셋 두 장을 지웠다.

**★ 레이어는 `SpriteComponent` **안**에 있다.**
컴포넌트를 여러 개 붙여도 레이어는 된다(붙인 순서 = 그리는 순서).
하지만 그러면 `Play()` · `SetTint()` · `SetScale()` 을 **N번씩** 불러야 하고,
이 프로젝트는 이미 「호출 한 줄을 안 옮겨 애니메이션이 멈추는」 버그를 냈다.
안에 두면 호출은 한 번이고, 위치·칸·틴트·반전이 한 곳에서 나오므로
**팔이 몸과 어긋나는 것이 구조적으로 불가능**해진다.

**★ 팔 좌표를 숫자로 적지 않는다.**
프레임마다 몸이 흔들리고 기울어진다(물기 행은 몸통이 8px 앞으로 나간다).
`tools/gen_player_arms.ps1` 이 칸마다 **몸통 색의 경계를 읽어** 거기에 붙인다.
몸 그림을 고치면 팔이 따라온다 — 두 번 고치지 않는다.

## 9. 엔진과 게임의 경계 **확정** (2026-09-10)

> 유용한 기능은 **엔진**에 두고, 게임 코드는 그것을 **조립하기만** 한다.
> Unity 가 하는 방식이다. 어려운 것은 목표가 아니라 **경계선을 어디에 긋는가**다.

### 두 방향으로 실패한다

```
너무 늦게 긋는다  ->  PlayScene.cpp 가 1,700줄이 된다
너무 일찍 긋는다  ->  아무도 안 쓰는 일반성이 쌓인다   ← 이쪽이 더 나쁘다
```

늦은 쪽은 **나중에 쪼갤 수 있다.** 이른 쪽은 지우기가 어렵다 —
「혹시 나중에 쓸지도 모른다」가 붙어 있어서 아무도 못 지운다.
그래서 판단 기준은 **미래 예측이 아니라 관찰**이어야 한다.

### ★ 규칙 — 두 번째 사용자가 생겼을 때 엔진으로 올린다

| 사용자 수 | |
|---|---|
| 하나 | 게임 코드에 둔다. 일반화하지 않는다 |
| **둘** | **엔진 후보.** 중복이 실제로 생겼다는 증거다 |
| 셋 | 확정. 안 올리면 세 곳이 어긋나기 시작한다 |

「두 번째 사용자가 있는가」는 **눈으로 셀 수 있는 사실**이라 판단이 흔들리지 않는다.
「나중에 쓸 것 같다」는 셀 수 없어서 항상 이쪽으로 기운다.

### 이 프로젝트는 이미 이 규칙으로 움직여 왔다

새 규칙이 아니라 **일어난 일에 이름을 붙이는 것**이다.

| 올라간 것 | 두 번째 사용자가 생긴 순간 |
|---|---|
| `AttackData` | 플레이어만 쓰다가 **적이 공격하게 되었다**(5-e-3) |
| `MakeAttackBox` | 좌우 반전 정규화가 **두 곳에 생겼다**(5-e-3) |
| `SlideDecaying` | 구르기 전용이다가 **넉백이 같은 식을 썼다**(5-e-3) |
| `Renderer::DebugDraw` | Scene 에 있다가 **틱 밖에서도 필요해졌다**(점검) |
| `Scene::Resume` | Death 가 「위가 닫혔다」를 알아야 했다(5-e-4) |

전부 **필요해진 뒤에** 올렸다. 그래서 지금 이 엔진에는 쓰이지 않는 일반성이 없다.

### Unity 와 대조

| Unity | 우리 | |
|---|---|---|
| `Time.fixedDeltaTime` | 고정 틱 60 | ✅ |
| `Input` | `Input` (키가 아니라 **의도**로 번역) | ✅ |
| `Camera` | `Camera` (뷰 행렬 · 흔들림) | ✅ |
| `AudioSource` | `Audio` (이름 · 팬 · 피치) | ✅ |
| `Animator` | `AnimationClip` + `AnimationPlayer` | ✅ |
| `SceneManager` | `Scene` / `SceneManager` (+ `Resume`) | ✅ |
| `Debug.DrawLine` | `Renderer::DrawRectOutline` 등 | ✅ |
| `Rigidbody2D` | — | ⚠ 6-c 에서 필요 |
| `Collider2D` (지형) | `AABB` 겹침만 | ⚠ 6-c 에서 필요 |
| `SpriteRenderer` | `Sprites().Draw(…인자 8개)` | 🔸 두 곳에서 반복 중 |
| `Transform` | `struct { x, y, facing }` × 2 | 🔸 두 번째 사용자 있음 |
| `GameObject` / 컴포넌트 | — | ❌ **아직 만들지 않는다** |

### ❌ 컴포넌트 시스템은 아직 만들지 않는다

`GameObject` + `Component` 는 **엔티티가 수십 종일 때** 값을 한다.
지금은 플레이어 1 + 적 1 이다. 지금 만들면 「두 개짜리를 위한 범용 프레임워크」가 되고,
그것은 1,700줄짜리 `PlayScene` 보다 고치기 어렵다.

적이 3~4종이 되고 투사체가 생기면 필요가 **저절로 드러난다.** 그때 만든다.

### 의존 방향은 한쪽이다

```
게임(Scene)  ──기능을 부른다──>  엔진(Renderer / Camera / Audio / Input / Physics)
게임(Scene)  <──아무것도 모른다──  엔진
```

`Renderer` 는 플레이어를 모르고 `Camera` 는 적을 모른다.
`SceneContext` 의 목록이 **엔진의 표면적 전부**이고, 그 목록이 짧게 유지되는 한
게임을 아무리 크게 만들어도 엔진은 흔들리지 않는다.

### 리팩터링은 기능 추가에 태운다

§8 과 `handoff.md §9` 가 기록하듯 **이 프로젝트의 최악 버그 2건이 전부 큰
리팩터링에서 나왔다**(2배속 · 애니메이션 정지). 문법이 멀쩡해 컴파일러가 못 잡는다.

그래서 「정리만 하는 큰 작업」을 따로 하지 않는다.
**그 기능이 실제로 필요로 하는 것만, 그 기능을 만들 때 올린다.**
