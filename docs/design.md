# DarkBubble 기획서

> 이 문서는 **비전**을 적는다. 숫자·대사·적 패턴처럼 바꾸기 싼 것은 여기서 확정하지 않는다.
> 「확정」 표시가 있는 항목만 구현의 전제로 삼는다.

## 0. 한 줄 요약

용에게 마을을 잃은 아이가 복수를 위해 나아가지만, 끝에서 **용도 피해자였다**는 것을 알게 되는
고정화면 2D 소울라이크 액션.

## 1. 핵심 컨셉

### 1.1 게임의 정체성 — 지문(指輪)

이 게임의 모든 지문은 **능력이 아니라 인식을 바꾼다.** 세상은 그대로인데, 내가 볼 수 있는 것이 늘어난다.

| 지문 | 보이게 되는 것 | 입수 |
|---|---|---|
| 初心者の指輪 | 적의 공격 예고(`!`) | 최초 |
| 蛍の指輪 | 어둠 속 | 보스 전리품 |
| 竜の指輪 | 용의 말 | 종반 |
| 亡者の指輪 *(제안)* | 그 방에서 과거에 일어난 일의 환영 | 미정 |
| 真実の指輪 *(제안)* | 적의 약점 부위와 남은 부위 HP | 미정 |

이 게임의 진실은 **최면술로 가려져 있다.** 용은 원래 적이 아니었다.

> **지문 = 가려진 진실을 벗기는 도구**

기획 전체가 이 한 줄로 묶인다. 새 아이템을 추가할 때 이 규칙에 맞는지 먼저 확인한다.

### 1.2 지문 슬롯 제한 — **확정**

**장착 슬롯은 2개.** 모든 지문이 「무엇을 포기할 것인가」의 선택이 된다.

> 어두운 동굴에서 강적을 만났다 → 蛍(밝기)을 뺄까, 初心者(공격 예고)를 뺄까?

蛍の指輪을 장착하지 않으면 횃불을 들어야 하고, 횃불은 한 손을 차지해 **양손 무기를 쓸 수 없다.**
이 기회비용이 지문 시스템의 핵심이다.

## 2. 스토리

### 2.1 서장

부모가 다급하게 아이를 깨우며 시작한다. 마을은 용의 습격을 받아 모두 도망치는 상황.
부모는 아이를 지키다 희생되고, 아이는 마을의 **유일한 생존자**가 되어 복수를 결심한다.

### 2.2 종반 — 입장의 역전

주인공이 **용의 마을을 습격한다.** 게임 시작과 정확히 반대 위치에 서게 된다.
이때 플레이어가 스스로 그 대칭을 알아채도록 연출한다. 설명하지 않는다.

### 2.3 결말

竜の指輪을 장착하고 마지막 용을 쓰러뜨리면, 죽기 직전 **최면술이 풀리며 흑막을 알려준다.**
진짜 흑막과 싸우게 되고, 쓰러뜨리면 모든 용에게 걸려 있던 최면이 풀린다.

다 끝났다고 생각한 순간 **아기 용이 다가온다.** 앞으로 사이좋게 지낼 가능성을 보여주며 끝.

## 3. 시스템

### 3.1 전투 — 스태미나제 **확정**

다크소울식 완전 스태미나제. **공격·구르기·가드가 전부 스태미나를 소모한다.**

| 항목 | 규칙 |
|---|---|
| 소모 | 공격 / 구르기 / 가드 시 피격 |
| 회복 | 행동 후 일정 시간(회복 지연) 뒤부터 자동 회복 |
| 고갈 | 회복될 때까지 아무 행동도 못 함 = 최대 위기 |
| 가드 | 스태미나로 데미지를 받아냄. 고갈되면 가드 붕괴 |

전투의 핵심 질문은 **「지금 둘러야 하나, 참아야 하나」**.
욕심내서 한 대 더 치면 구를 스태미나가 없다 — 이 긴장이 게임 전체의 리듬이 된다.

> 적 패턴은 **스태미나 경제를 기준으로 설계한다.**
> 「연속 3타 후 빈틈」이 아니라 「연속 3타를 다 구르면 스태미나가 바닥난다」로 설계할 것.

### 3.1.1 강인도(poise) — 경직을 데이터가 정한다 **확정**

맞았을 때 경직에 걸리는지 아닌지를 코드가 아니라 **숫자가 결정한다.**

```
방어구의 강인도(poise)  >=  적 공격의 충격력(impact)   →   데미지만. 자리에서 버틴다
방어구의 강인도(poise)  <   적 공격의 충격력(impact)   →   경직 + 넉백 + 피격 무적
```

**Why:** 「경직을 둘까 말까」는 게임 전체를 가르는 질문인데, 코드로 고정하면
그 답이 하나뿐이 된다. 숫자로 두면 **방어구 하나하나가 다른 게임**을 만든다.
상태 머신 원칙(「상태는 안 늘어나고, 다양성은 데이터에서」)의 또 하나의 적용이다.

★ **버티기는 안전한 것이 아니라 다른 지불 방식이다.**

| | 회피 | 버티기 |
|---|---|---|
| 지불 수단 | **스태미나** | **HP** |
| 요구 | 타이밍 | 장비 |
| 실패 시 | 경직 + 데미지 | (없음. 확정 데미지) |

이 대비가 방어구를 「강함」이 아니라 **선택**으로 만든다. 그래서 미결정이었던
「방어구: 무게 → 구르기 속도 연동?」의 답도 여기서 나온다:

```
가벼운 방어구   poise 낮음 → 경직 O   구르기 빠름   →  「흘려서 산다」
무거운 방어구   poise 높음 → 경직 X   구르기 느림   →  「버텨서 산다」
```

지문 슬롯 2개와 **같은 종류의 기회비용**이다.

**방식은 문턱(threshold)** — 단순 비교다(다크소울 1식). 게이지가 깎이고 회복되는
소모 방식(다크소울 3식)은 「3타 중 2타는 버티고 3타에 무너진다」를 만들 수 있지만,
문턱이 「내 방어구로 이 적을 버틸 수 있나」를 한 번의 실험으로 학습시킨다.
나중에 바꾸려면 위의 비교 한 줄이 게이지 감산으로 바뀔 뿐이다.

> **충격력(impact)은 데미지와 다른 숫자로 둔다.** 합치면 「약하지만 크게 휘청이게
> 하는 공격」(방패 밀치기 같은 것)을 만들 수 없다.

### 3.1.2 무적 프레임의 처리 방식 **확정**

구르기의 무적 구간이 적 공격의 지속 구간과 겹쳤을 때:

> **무적인 틱은 없었던 일로 한다.** 그 휘두르기를 소진시키지 않는다 —
> 무적이 풀린 다음 틱에 지속 구간이 남아 있으면 **그때 맞는다.**

「무적 프레임」이 문자 그대로 동작하는 쪽을 택했다. 한 틱만 스쳐도 그 공격을
통째로 흘리는 방식(관대함)은 **별개 규칙**이고, 그건 나중에 **패링(parry)** 을
만들 때 쓸 개념이다. 지금 섞으면 둘 다 애매해진다.

무적 12틱 > 지속 4틱 이므로 타이밍만 맞으면 완전 회피가 된다.

### 3.1.3 스턴락 방지 **확정**

경직 중에 또 맞으면 경직이 0부터 다시 시작한다. 적이 두 마리면 영원히 못 움직인다.
이것이 스턴락이고, 「억울하게 죽었다」는 감각의 원인이다.

> **피격 무적 길이 > 경직 길이.** 경직이 풀리고 **나서도 조금 더** 안전해야 한다.
> 같게 두면 경직이 풀리는 그 틱에 다시 맞는다.

★ 무적이 두 종류가 되고, **성격이 다르다.**

| | 구르기 무적 | 피격 무적 |
|---|---|---|
| 누가 주는가 | 플레이어가 **벌어낸다**(스태미나 + 타이밍) | 게임이 **준다** |
| 정체 | 게임 디자인 — 재미를 만든다 | 게임 공학 — 불공평을 막는다 |
| 표현 | 색 (푸르게) | 깜빡임 |

★ 피격 무적은 **경직의 부속품**이다. 강인도로 버텨내면 못 움직이는 구간이
없으므로 스턴락 위험도 없고, 그래서 피격 무적도 주지 않는다.

### 3.2 부위 파괴 — 핵심 시스템 **확정**

**모든 적이 부위별 HP를 가진다.** 이 게임의 최대 차별점.

| 부위 | 파괴 시 |
|---|---|
| 다리 | 이동 불가. **기어서 쫓아온다** |
| 팔 | 그 팔의 무기를 떨군다 |
| 머리 | **격파** (HP 가 몸통의 1/5) |
| 몸통 / 코어 | 격파 |

전술적 선택이 매 전투마다 생긴다 — 빠른 적은 다리, 강타형 적은 팔.

### 머리 = 즉사 **확정** (2026-09-09 변경)

원안은 「시야 상실 → 소리로만 쫓는다」였다. **폐기한다.**

**Why:** 소리 전파와 수색 AI 가 필요해 비용이 다른 부위 파괴 전부를 합친 것보다 크다.
그리고 즉사가 **보상으로 더 명확하다** — 「머리 HP 는 몸통의 1/5 이지만 상자가
작고 높다」는 위험/보상 관계가 설명 없이 전달된다.

이 결정으로 §1.1 의 「머리 파괴의 대칭성 — 蛍の指輪을 빼면 *내가* 어둠 속에 있고,
머리를 부수면 *적이* 어둠 속에 있다」는 **아이디어는 폐기된다.** 아까운 대칭이지만
그 대칭을 위해 청각 시스템 하나를 만들 값은 아니다.

**How to apply:** 부위 파괴 처리에서 `머리 또는 몸통 → 격파`. 다리는 그대로
「이동 불가」다. 「다리만 베었는데 격파는 비현실적」이라는 출발점은 유지된다.

> ★ 그리고 이 결정으로 **판정 상자만으로 조합이 완성됐다.**
> 다리를 부수면 적이 엎드리고, 엎드린 자세의 머리 상자가 앞으로 튀어나오면서
> 기본 공격 높이에 들어온다.
>
> ```
> 다리(40) 4방 → 기어옴 → 머리(20) 2방 = 6방
> 몸통 정면                            = 9방
> ```
>
> 「부위를 노리면 빨리 죽는다」가 새 코드 없이 데이터에서 나왔다.
> 다만 엎드린 적도 물어뜯으므로(사거리 짧고 후딜 길게) 리스크는 남는다 —
> 「다리를 부수면 완전 무력화」로 만들면 항상 다리부터 노리는 것이 정답이 되어
> 이 절의 전술적 선택이 사라진다.

### 3.2.1 무기 모션이 노리는 부위를 결정한다 **확정**

무기마다 모션이 다르고, **모션에 따라 닿는 부위가 다르다.**

| 모션 예 | 히트박스 높이 | 주로 닿는 부위 |
|---|---|---|
| 서서 약공격 | 몸통 높이 | 몸통 |
| **웅크려 공격** | 발밑 근처 | **다리** |
| 위로 베기 / 찌르기 | 머리 높이 | 머리 |
| 대검 내려찍기 | 넓게 전부 | 겹침 면적이 큰 쪽 |

**Why:** 부위 파괴가 「우연히 어디가 맞았나」가 아니라 **플레이어가 조준하는 행위**가 되어야
전술이 생긴다. 「다리를 봉쇄하려면 웅크려서 쳐라」가 성립하는 순간
기획서 3.2 의 부위 파괴가 실제로 게임이 된다.

**How to apply:** 코드는 이미 준비되어 있다. `AttackData.heightFromFoot` 하나로
닿는 부위가 바뀐다(겹침 면적으로 부위를 고르므로). 남은 것은 **데이터 구조**다.

```
무기 하나  =  공격 여러 개(무브셋)
    dagger.light        heightFromFoot 34   → 몸통
    dagger.crouch       heightFromFoot 10   → 다리
    dagger.thrust       heightFromFoot 48   → 머리
```

**입력 맥락이 어느 공격인지 결정한다.**

| 상태 / 입력 | 나가는 공격 | 닿는 부위 |
|---|---|---|
| 서서 + 공격 | light | 몸통 |
| **Ctrl** + 공격 | crouch | **다리** |
| 달리며 + 공격 | running | 몸통 (길게 뻗는다) |
| 공격 중 + 공격 | 2타 = thrust | **머리** |

### 선택 규칙 **확정** (2026-09-10 구현)

> **명시적 입력이 암묵적 맥락을 이긴다.** 그다음은 암묵적 맥락끼리 구체적인 것부터.

```
① Ctrl 을 누르고 있다   -> crouch     (지금 누르고 있는 것이 가장 최신 의도다)
② 공격 중이었다         -> 2타
③ 달리고 있었다         -> running
④ 그 밖                 -> light
```

**웅크리기는 상태가 아니라 수식자(modifier)다.** `PlayerState` 는 6개 그대로다.
웅크린 자세의 **피격 판정**이 실제로 달라져야 할 때 상태로 승격하면 된다.

※ 이 게임은 상하좌우로 다 움직이는 벨트스크롤 방식이라 「아래 방향키」를
웅크리기로 쓸 수 없다 — 그건 이동이다. 그래서 `Ctrl` / 패드 `LB` 를 배정했다.

### 무브셋이 만들어낸 것

★ **「머리를 노리려면 콤보를 성공시켜야 한다」가 데이터만으로 성립했다.**
머리는 즉사(§3.2)이고 thrust 는 1타를 낸 뒤에만 나오므로,
새 규칙을 한 줄도 안 쓰고 리스크/보상이 생긴다.

★ **스태미나 경제(§3.1)와 맞물린다.**
`light(28) + thrust(34) = 62`. 100 중 62를 쓰면 38 이 남고 구르기는 30 이므로,
**콤보 뒤에는 한 번밖에 못 구른다.** 「욕심내서 2타를 넣을까, 남겨서 구를까」가
매 순간의 질문이 된다 — §3.1 이 요구한 바로 그 긴장이다.

★ **웅크리기는 느리다**(이동 0.45배). 조준의 대가다.
「다리를 봉쇄하려면 멈춰서 노려야 한다」가 이동 속도 한 줄로 만들어진다.

### 선택 사항 — 프레임별 히트박스 (스윙 궤적)

지금은 active 구간 내내 히트박스가 **한 자리에 고정**되어 있다.
실제 칼은 호를 그리므로, 프레임마다 히트박스를 다르게 두면 훨씬 자연스럽다.

```
t8   히트박스 (높이 48)  ← 위에서
t9   히트박스 (높이 32)  ← 중간
t10  히트박스 (높이 16)  ← 아래로
```

이렇게 하면 **닿는 타이밍에 따라 맞는 부위가 달라진다.** 격투게임이 실제로 쓰는 방식이다.
데이터가 늘어나므로 무브셋 구조가 정착된 뒤에 검토한다.

### 3.3 성장 — 3단계 **확정**

스토리 분기점에서만 변한다. **강화가 아니라 트레이드오프.**

| 단계 | 얻는 것 | 잃는 것 |
|---|---|---|
| 아이 | 몸이 작아 구르기가 빠르고 피격 판정이 작다 | 무거운 무기를 못 든다 |
| 소년 | 균형 | — |
| 청년 | 대형 무기, 높은 공격력 | 구르기가 느리고 몸집이 크다 |

「어릴 때가 오히려 피하기 쉬웠다」— 성장을 **상실을 동반한 변화**로 만든다. 복수극의 주제와 맞다.

> 3단계로 제한하는 이유는 **스프라이트 비용**이다. 나이별로 애니메이션 한 벌이 통째로 늘어난다.

### 3.4 주인공 — 1명 **확정**

스타팅 캐릭터 복수안은 채택하지 않는다. 주인공은 **「마을의 유일한 생존자인 아이」 한 명**이다.
「유일한 생존자」라는 서사가 이 게임의 출발점이므로 이것을 우선한다.

*(선택안: 「도망칠 때 무엇을 집어 들었는가」로 시작 무기만 분기시키면 리플레이 가치를 확보할 수 있다. 보류)*

### 3.5 기도 포인트 (세이브)

기도하는 곳에서 기도하면:

- 세이브
- HP / MP 회복
- 기도 포인트 간 텔레포트

**기도의 말이 진행도에 따라 바뀐다.** 구현은 문자열 테이블 하나지만 효과가 크다.

```
서장   "아버지, 어머니… 무서워요."
중반   "반드시 갚아주겠습니다."
종반   "……제가 틀렸던 걸까요."
```

플레이어는 같은 장소에서 같은 행동을 반복하는데, **자기 캐릭터가 변해가는 것을 문장으로 목격**한다.

> **미결정**: 기도하면 적이 부활하는가? (부활 → 파밍 가능·긴장감 / 비부활 → 탐험이 편함)

### 3.6 사망

`You died` 대신, 부활하면서 **멋진 대사**가 나온다 (「할 일을 해라」 같은 톤).

**한 줄 고정이 아니라 테이블로 둔다.** 진행도별 또는 사인(死因)별로 다른 대사.
시스템 비용은 같은데 플레이어가 「어, 아까랑 다르네?」를 발견하는 순간이 생긴다.

> **대사 테이블은 보류** (2026-09-10). 폐기가 아니다.
> BitmapFont 가 ASCII 전용이라 한국어·일본어 대사를 화면에 쓸 수 없다
> (§6.5 의 「런타임 글리프 아틀라스」가 먼저 필요하다).
> 지금은 `DeathScene` 의 문자열 한 줄이므로, 폰트가 생기면 그 자리에 테이블을 끼운다.

### 3.6.1 죽으면 무엇이 되돌아가는가 **확정**

> **죽었을 때 무엇이 되돌아가고 무엇이 남는가 — 그것이 이 게임이 무슨 게임인지를 정한다.**

| | 되돌아간다 | 남는다 |
|---|---|---|
| 플레이어 HP · 스태미나 · 위치 · 상태 | ✓ | |
| **적** (부위 HP 포함) | **✓ 되살아난다** | |
| 열어둔 문 · 얻은 아이템 | | ✓ (7단계) |

**Why:** 전부 되돌리면 벌이 너무 크고, 아무것도 안 되돌리면 죽음이 무의미해진다.
「적은 되살아나지만 열어둔 문은 열린 채」가 소울류의 리듬 그 자체다.
적이 되살아나야 §3.1 의 스태미나 경제가 매번 다시 시험된다.

**How to apply:** `PlayScene::Respawn()` 하나가 이 표다.
★ **초기화(`Enter`)가 이 함수를 부른다.** 초기화와 부활은 같은 일이므로
두 벌로 만들면 반드시 어긋난다 — 필드를 추가할 때 한쪽만 고치게 되고
「두 번째 판부터 뭔가 이상하다」는 재현하기 어려운 버그가 된다.

부활 지점은 지금 방 하나뿐이라 시작 위치 고정이다.
§3.5 의 기도 포인트가 들어오면 그것이 부활 지점이 된다(7단계).
「기도하면 적이 부활하는가」는 이 결정에 따라 **부활한다**로 정리된다 —
죽음과 기도가 같은 규칙을 쓰는 편이 플레이어에게 설명하기 쉽다.

## 3.7 내부 해상도 — 640×360 (×2 확대) **확정**

창은 1280×720 이지만, 게임은 **640×360 렌더 타겟에 그린 뒤 정수 2배로 확대**한다.

| 항목 | 값 |
|---|---|
| 내부 해상도 | 640 × 360 |
| 화면 확대 | ×2 (= 1280 × 720) |
| 캐릭터 크기 목표 | 48 ~ 64 px |

**Why:** 도트 게임에서 네이티브 1280×720 으로 그리면 스프라이트 하나에 드는 시간이
4~16 배가 되어 혼자서는 완성할 수 없다. 반대로 320×180 은 그림 작업은 가장 적지만
**부위별 파괴(팔·다리·머리)와 방어구 차이를 보여줄 수 없다.** 640×360 이 그 사이의 균형점이다.

**How to apply:** 좌표·이동 속도·히트박스 오프셋은 모두 640×360 기준으로 적는다.
1280×720 기준 숫자를 쓰면 안 된다. 확대는 마지막에 한 번만 일어난다.

구현 방식: 게임을 640×360 텍스처에 그리고(RTV), 그 텍스처를 화면에 ×2 로 그린다(SRV).
같은 텍스처에 RTV 와 SRV 를 둘 다 만드는 구조이며, **포스트 프로세싱(비네팅·색보정·블룸)의
토대가 그대로 생긴다.** 창 크기 변경도 레터박스로 자동 해결된다.

> 2026-09-07 시점: **결정만 되어 있고 아직 구현하지 않았다.** 현재 코드는 1280×720 네이티브다.

## 3.8 시점과 이동 — **플랫포머** **확정** (2026-09-10)

> **측면 뷰 + 중력 + 점프.**

### 문서에 있던 모순을 여기서 정리한다

`README.md` 와 `handoff.md` 는 처음부터 **「버블보블 같은 고정화면 2D」**라고 적어
두었는데, 아래 §4 는 참조로 **젤다 1편 / Binding of Isaac**(탑다운)을 들고 있었다.
그리고 코드는 그 사이에서 **벨트스크롤**(`y` = 깊이, 상하좌우 자유 이동)로 흘러갔다.

**세 개가 서로 다른 게임이었다.** 버블보블이 원래 의도이므로 그쪽으로 맞춘다.

### 무엇이 바뀌는가

| | 지금 (벨트스크롤) | 앞으로 (플랫포머) |
|---|---|---|
| `y` 의 의미 | **깊이** (화면 안쪽) | **높이** (중력이 당긴다) |
| 이동 | 상하좌우 자유 | **좌우만** + 점프 / 낙하 |
| 바닥 | 화면 아래쪽 clamp 하나 | **발판 사각형 목록** |
| 세로 위치 | 플레이어가 직접 정한다 | 중력과 점프가 정한다 |

**Why:** 「고정화면 한 장에서 싸운다」는 §4 의 결정과 플랫포머는 잘 맞는다 —
버블보블이 정확히 그 구조다. 그리고 부위 파괴(§3.2)는 **측면 뷰에서 훨씬 잘 읽힌다.**
머리·몸통·다리가 화면에서 위아래로 늘어서므로 「낮게 치면 다리」가 눈에 보인다.
탑다운이었다면 부위가 겹쳐 보여 이 게임의 핵심 시스템이 전달되지 않는다.

### 이미 만든 것 중 살아남는 것

거의 전부다. 이것이 상태 머신 · 프레임 데이터로 만들어 둔 값이다.

| 시스템 | |
|---|---|
| 상태 머신 · 프레임 데이터 · 스태미나 · 강인도 | 그대로 |
| 부위 파괴 · 판정 상자 | **오히려 더 잘 맞는다**(위 참조) |
| 무브셋 (`heightFromFoot`) | 그대로. 「발끝에서 몇 픽셀 위」가 실제 높이가 되어 의미가 더 명확해진다 |
| 사망 · 부활 · Scene 스택 | 그대로 |
| 카메라 | 여전히 불필요 (고정화면) |

### 바꿔야 하는 것

| 항목 | 내용 |
|---|---|
| 중력 · 점프 | 새 데이터(중력 가속도 · 점프 초속 · 최대 낙하 속도) |
| 지면 판정 | 발판 사각형 목록과의 충돌. 고정화면이므로 **타일맵은 불필요** — 사각형 몇 개면 된다 |
| 적 추격 | 2차원 접근 → **1차원 + 중력.** 낭떠러지에서 멈추는 판정이 필요해진다 |
| 넉백 | 수평 + 약간의 상승이 자연스럽다 |
| 구르기 | 지상에서만 |

### 3.8.1 점프는 **상태**다 **확정**

`PlayerState` 에 공중 상태를 추가한다. 상태가 **8개**가 된다
(Idle / Run / Attack / Roll / Exhausted / Hurt / Dead / **Jump**).

**Why:** 「상태는 6개에서 안 늘어난다」는 원칙의 진짜 내용은
**「조건이 여러 곳에 흩어지기 시작하면 상태로 승격한다」**였다. 공중은 그 기준을 넘는다 —
이동 제어가 다르고(공중 제어력), 구르기가 안 되고, 착지 판정이 필요하고, 공격이 다르다.
이 넷을 `if (!grounded)` 로 흩뿌리면 상태 머신을 만든 이유가 사라진다.
원칙 위반이 아니라 **원칙의 적용**이다.

> 다양성은 여전히 데이터에서 나온다 — 공격이 5종이어도 `Attack` 은 하나다(§3.2.1).

### 3.8.2 점프 중 공격 **확정**

무브셋에 `jump` 가 하나 늘어난다(§3.2.1).

★ 공중에서 내려찍으면 **머리에 닿기 쉽다** — 적보다 위에 있기 때문이다.
머리는 즉사(§3.2)이므로 「높은 곳에서 뛰어내려 머리를 노린다」가 성립한다.
지형(발판)이 전술의 일부가 되는 순간이고, 이것이 플랫포머로 옮기는 진짜 이득이다.

### 3.8.3 웅크리기 키는 `Ctrl` 유지 **확정**

↓ 방향키가 플랫포머의 관례지만 `Ctrl` 을 유지한다.
↓ 는 나중에 **아래 발판으로 내려가기**(내려찍기 / 통과 가능한 발판)에 쓸 여지가 있고,
조작을 한 번 익힌 뒤 바꾸는 비용이 크다.

### 미결정

| 항목 | 메모 |
|---|---|
| 공중 제어력 | 점프 중에 좌우로 얼마나 조종되는가. 0 이면 「뛰면 끝」, 1 이면 공중에서 자유롭게 |
| 이단 점프 · 벽 타기 | 있는가. 있으면 지형 설계가 통째로 달라진다 |
| 낙하 데미지 | 소울류에는 있다 |

## 3.9 시야 (FOV) — **A · B 둘 다 확정** (2026-09-10)

> 「현실처럼 보이는 범위를 제한한다」. **둘은 같은 규칙의 양면이다.**

### A. 플레이어의 시야 — 어둠

화면 전체가 어둡고, 플레이어 주변과 **바라보는 방향**만 보인다.

★ **이미 기획서의 뼈대다.**
§1.1 의 `蛍の指輪`(「어둠 속이 보이게 된다」)와 §4 의 `暗黒の洞窟` 이 이것을 전제로 적혀 있다.
그리고 §1.2 의 지문 슬롯 2개의 기회비용도 여기서 성립한다 —
「蛍을 빼면 횃불을 들어야 하고, 횃불은 한 손을 차지해 양손 무기를 못 쓴다」.

**즉 이 시스템이 없으면 蛍の指輪 은 존재할 수 없다.**

구현: 캔버스에 다 그린 뒤 마스크를 곱한다.
★ **2패스 구조가 이미 있어서 3패스로 늘리면 된다.** §3.7 이
「포스트 프로세싱(비네팅·색보정·블룸)의 토대가 그대로 생긴다」고 적어 둔 바로 그 자리다.

### B. 적의 시야 — 인지

적이 플레이어를 감지하는 범위를 **원형 거리에서 방향 있는 부채꼴로** 바꾼다.
지금은 `kEnemySightRange` 가 단순 거리라서 **등 뒤에 있어도 본다.**

뒤에서 다가가면 안 보인다 → 기습이 성립하고, 「어느 쪽에서 접근할까」가 판단이 된다.

구현: 싸다. 거리 판정에 각도 하나를 더하는 정도다.

### ★ 둘은 같은 규칙의 양면이다

§3.2 에 이렇게 적혀 있었다 —

> **머리 파괴의 대칭성**: 蛍の指輪을 빼면 *내가* 어둠 속에 있고,
> 머리를 부수면 *적이* 어둠 속에 있다. 같은 규칙이 양쪽에 적용된다.

머리 = 즉사로 정하면서(§3.2) 이 대칭을 폐기했는데, **FOV 를 넣으면 되살아난다.**
A 는 내 시야, B 는 적의 시야이고, 「보이지 않으면 싸울 수 없다」가 양쪽에 걸린다.

### 미결정

**순서는 B 먼저, A 나중.** B 는 각도 판정 하나라 싸고 즉시 게임을 바꾸고,
A 는 렌더 패스를 하나 늘려야 하지만 蛍の指輪의 전제라 반드시 온다.

| 항목 | 메모 |
|---|---|
| A 의 모양 | 원형(등불) / 부채꼴(방향) / 둘의 합 |
| A 를 항상 켤까 | 밝은 곳에서는 끄고 동굴에서만? 「어둠」이 **장소의 성질**이 된다 |
| B 를 적이 잃으면 | 머리 파괴 = 즉사로 정했으므로, 대신 「등 뒤 기습」이 그 역할을 한다 |

## 4. 맵 구조 — 넓은 맵 + 카메라 추적 **확정** (2026-09-10 변경)

화면보다 **넓은 맵**을 만들고, 카메라가 플레이어를 따라 움직인다.
측면 뷰 플랫포머(§3.8)이므로 좌우로 길고 위아래로도 층이 있는 맵이 된다.

### 예전 결정(고정화면 방 그래프)을 뒤집었다

원안은 「화면은 항상 한 장, 문으로 나가면 다음 방」(젤다 1편 / Binding of Isaac 식)이었고,
그 근거는 **비용**이었다. 뒤집었으므로 그 이점들이 전부 사라진다. 정직하게 적어 둔다.

| 잃는 것 | 대신 필요한 것 |
|---|---|
| 「카메라 시스템이 필요 없다」 | 카메라 추적 · 맵 경계 clamp · 데드존 |
| 「타일맵 스트리밍 불필요」 | 화면 밖 지형·적을 어떻게 다룰지(컬링) |
| 「세이브가 단순 — 어느 방에 있었나 하나」 | 맵 + 좌표. §3.5 기도 포인트가 그 역할을 한다 |
| 「방 하나씩 = 작업 단위가 명확」 | 맵 하나가 커져서 한 덩어리의 작업량이 늘어난다 |

**Why(그럼에도 뒤집는 이유):** 고정화면은 「한 화면 안에서 벌어지는 일」로 게임을 가두고,
넓은 맵은 **탐험**을 가능하게 한다. 소울라이크의 「길이 이어져 있다는 감각」과
§1.1 의 지문 시스템(어둠 · 환영 · 숨은 것)은 넓은 공간에서 훨씬 강하게 작동한다.

### 다행히 절반은 이미 만들어져 있다

`Camera` 클래스가 이미 있다 — 위치 · 줌 · 화면 흔들림 · 뷰 행렬.
화면 흔들림 때문에 만들었던 것이 그대로 추적 카메라의 토대가 된다.
그리고 **2패스 저해상도 캔버스(640×360)는 그대로 유효하다** — 카메라가 움직여도
내부 해상도는 바뀌지 않는다(§3.7).

```
    [집]───[마을 길]───[광장]
                          │
                     [기도의 장소]
                          │
                   [동굴 입구]───[暗黒の洞窟]───[보스]
```

맵**들**을 잇는 구조 자체는 남는다. 달라지는 것은 **한 칸의 크기**다 —
「화면 한 장」이 아니라 「화면 여러 장 넓이의 구역」이 된다.

### 미결정

| 항목 | 메모 |
|---|---|
| 지형 표현 | 사각형 목록 / 타일맵. 넓어지면 사각형 목록은 관리가 어려워진다 |
| 카메라 추적 방식 | 즉시 따라가기 / 지연 / 데드존(가운데 상자 안에서는 안 움직임) |
| 세로 스크롤 | 좌우만인가, 위아래도인가 |
| 맵 경계 | 카메라가 맵 밖을 안 보이게 clamp 한다(관례) |

### 에리어

2. **暗黒の洞窟** — 蛍の指輪의 무대
3. (미정)
4. 용의 마을 (종반)
5. 흑막 (최종)

## 5. 스토리 전달 방식 — 컷신을 쓰지 않는다 **확정**

고정화면 게임에서 컷신은 비싸다(전용 연출·카메라·스크립트).
다크소울이 실제로 쓰는 방법을 그대로 쓴다.

| 수단 | 비용 | 쓰이는 곳 |
|---|---|---|
| 방 자체의 배치 | 무료 | 불탄 집, 뒤집힌 요람 |
| 亡者の指輪의 환영 | 낮음 | 부모의 마지막, 용의 기억 |
| 기도의 말 | 매우 낮음 | 주인공의 심경 변화 |
| 보스의 임종 대사 | 낮음 | 마지막 용의 최면 해제 |
| 아이템 설명문 | 매우 낮음 | 지문마다 짧은 유래 |

**플레이어가 스스로 찾아낸 이야기는 들려준 이야기보다 오래 남는다.**

## 6. 縦切り(첫 목표) — 「마을의 밤」

전체를 만들기 전에 **이것 하나만 완성한다.**

| 요소 | 목표 |
|---|---|
| 방 | 5개 (집 → 마을 길 → 광장 → 기도의 장소 → 용이 있는 언덕) |
| 무기 | 1개 (단검) |
| 지문 | 1개 (初心者の指輪) |
| 적 | 2종 |
| 보스 | 1체 |
| 시스템 | 이동 · 공격 · 구르기 · 스태미나 · 부위 파괴 · 기도 · 사망 · 부활 |

이 5개 방이 재밌으면 **나머지는 전부 콘텐츠 추가**다 — 구조를 다시 짤 일이 없다.
재미없으면 **방 5개 만들고 알아낸 것이다. 50개가 아니라.**

스토리 도입부 그대로이므로, 완성하면 **그 자체로 체험판**이 된다.

## 6.5 대화 시스템 (엔진 기능으로 예정) — 미착수

「컷신을 쓰지 않는다」(5장) 결정 때문에 **텍스트가 서사 전달의 거의 전부**다.
그래서 대화는 게임 코드가 아니라 **엔진이 제공하는 기능**이어야 한다.

### 표시 방식 두 가지

| 방식 | 쓰이는 곳 |
|---|---|
| **말풍선** — 캐릭터 옆에 붙어 따라다닌다 | 짧은 대사, 적의 임종 대사, 기도의 말 |
| **전체 화면** — 하단 또는 전면 상자 | 긴 대화, 아이템 설명, 亡者の指輪의 환영 |

★ 둘은 **표시 방법만 다르고 진행 로직은 같다.**
「대사 목록을 순서대로 넘긴다」는 부분(DialogueRunner)을 공유하고,
말풍선/전체화면은 그것을 그리는 뷰(View)로만 나눈다. 로직을 두 벌 만들지 않는다.

### 데이터 형식 — 미결정

대사를 코드에 박으면 안 된다. 외부 파일로 뺀다.

| 후보 | 장단 |
|---|---|
| JSON | 6단계에서 어차피 도입. 구조가 명확하지만 긴 문장을 쓰기엔 답답 |
| CSV / TSV | 표 형태라 번역·검수에 강함. 분기 표현이 약함 |
| 전용 스크립트 (Ren'Py / Yarn Spinner 식) | 사람이 쓰기 가장 편하고 분기·조건에 강함. 파서를 직접 만들어야 함 |

**대사 ID → 텍스트 테이블** 구조를 권한다. 코드는 ID 만 알고,
언어 전환이 테이블 교체로 끝난다(한국어/일본어/영어).

### 알려진 장애물

- **폰트**: 현재 BitmapFont 는 ASCII 전용. 한국어·일본어는 글자 수가 많아
  전부 미리 굽는 방식이 통하지 않는다. **런타임 글리프 아틀라스**가 따로 필요하다.
  (필요한 글자가 나올 때마다 아틀라스에 채워 넣는 방식)
- **타자기 효과**: 한 글자씩 나타나는 연출. 틱 단위로 세면 되므로
  고정 타임스텝 덕에 쉽다. 「n 틱마다 한 글자」.
- **줄바꿈**: 상자 폭에 맞춰 단어 단위로 접기. 한국어·일본어는 단어 경계가
  공백이 아니라서 규칙이 다르다.

## 8. 기술적 영향

기획 확정에 따라 원래 로드맵에 생기는 변화.

### 8.1 부위 파괴 → 적은 단일 스프라이트가 될 수 없다

가장 큰 영향. 적이 「팔이 잘린 상태」를 표시해야 하므로 **스프라이트 구조가 달라진다.**

| 방식 | 장점 | 단점 |
|---|---|---|
| 부위별 스프라이트를 겹쳐 그림 | 조합 폭발 없음 | 관절이 뻣뻣해 보이기 쉬움 |
| 상태별 애니메이션 세트를 따로 그림 | 보기 좋음 | 그림 양이 상태 수만큼 배증 |
| **하이브리드(권장)** | 다리 파괴만 전용 애니메이션(기기), 팔·머리는 겹쳐 그리기로 제거 | |

**로드맵 2단계(SpriteBatch)와 4단계(스프라이트시트 애니메이션)에 영향.**
나중에 고치면 비싸므로, 4단계 설계 시 「적 = 파츠의 집합」을 전제로 만든다.

### 8.2 데이터 구조

```
enemies.json
  parts: [ { name, hp, hitbox, onBreak } ]     ← 부위별
  ai:    { sight, hearing, onLegBreak, ... }

weapons.json
  actions: [ { name, frames, hitbox, staminaCost, damage } ]
                                  ~~~~~~~~~~~~ 스태미나 항목 추가
```
